## 3．P1 结果

### 3.1 `842570f`：提取共享计划数据

`GeneratedAdventurePlan.PlannedBiomePatch` → `plan.PlannedBiomePatch`。

`planner` 产出该类型而 `runtime` 组装 planner 对象，`planner` 与 `runtime` 因此构成真实的包环。地块归属、边界与面积属于共享计划数据，移入 `plan` 后规划器不再 import 运行时计划类。记录的字段名与顺序未变，`PlanV2Codec` 按显式字段名读写，线格式不变。

### 3.2 `c67e360`：进度观察接口

新增 `plan.PlanningStage`（由 `PlanningProgress.Stage` 移动而来，常量名、区间与翻译键不变）与 `plan.PlanningObserver`（只有 `stage`／`detail`／`within` 三个方法，含 `NONE` 实现）。

`PlanningProgress.Run` 实现该接口，`RuntimePlanner` 把当前运行显式传给 `JointPlanner`、`ClimatePlan`、`FillerLayout` 与 `GeneratedAdventurePlan`。原先算法直接调用的静态 `stageCurrent`／`withinCurrent`／`detailCurrent` 全部删除。

结果：`planner` 不再 import `runtime`，这原是 P1 的出口条件。进度只作观察，仍不参与生成、重试或随机输入。

### 3.3 `db9512b`：迁移公共噪声与缓存工具

| 原位置 | 新位置 |
|---|---|
| `terrain.ValueNoise` | `noise.ValueNoise` |
| `terrain.ContinuousDomainWarp` | `noise.ContinuousDomainWarp` |
| `planner.CellMask` | `spatial.CellMask` |
| `runtime.ColumnQueryCache` | `spatial.ColumnQueryCache` |

对应测试随生产包迁移。纯位置调整：无方法、常量、数值或顺序改动。地形不再伸入 `runtime`，计划数据不再伸入 `planner`，`noise` 不依赖规划或运行时。

### 3.4 `6354506`：隔离数据包加载

`config.ProfileManager` 是 `config` 中唯一的 Minecraft 依赖（继承 `SimplePreparableReloadListener`、读取数据包资源）。按规划给 `config` 划定的边界拆开：

- `config.LoadedProfile`：纯结果数据（身份、已校验配置、规范化 JSON、输入哈希、来源包），无 Minecraft 类型。
- `worldgen.ProfileReloadListener`：持有资源栈、固定资源位置与当前 profile 注册表，产出 `LoadedProfile`。

`config` 现在零 Minecraft import；`RuntimePlanner` 改用 `LoadedProfile` 而非 reload listener 的嵌套类型。控制流、校验规则、错误码、冲突检测与规范化 JSON 身份均未改变。

### 3.5 `PackageBoundaryTest`：边界守卫

4 项源码级检查，防止后续改动悄悄恢复已移除的依赖：

| 检查 | 断言 |
|---|---|
| `configLayerHasNoMinecraftOrNeoForgeDependency` | `config` 不 import `net.minecraft` / `net.neoforged` |
| `planningAlgorithmsDoNotDependOnTheRuntimeLayer` | `planner` 不 import `...runtime` |
| `planDataDoesNotDependOnPlanningOrRuntime` | `plan` 不 import `...planner` / `...runtime` |
| `sharedNoiseToolsDoNotDependOnPlanningOrRuntime` | `noise` 不 import `...planner` / `...runtime` |

已人工验证其有效性：向 `planner/StableIds.java` 注入一行 `...runtime.RuntimePlanner` 的 import 后，`planningAlgorithmsDoNotDependOnTheRuntimeLayer` 立即失败；移除注入后恢复通过。

## 4．P1 出口条件核对

《重构规划》对 P1 的出口要求是"算法不依赖具体运行时数据类或静态界面进度；输出基线一致"。

| 要求 | 结论 | 证据 |
|---|---|---|
| 算法不依赖具体运行时数据类 | 满足 | `planner` 无 `...runtime` import；由 `PackageBoundaryTest` 守护 |
| 算法不依赖静态界面进度 | 满足 | 静态 `stageCurrent`／`withinCurrent`／`detailCurrent` 已删除；改为显式 `PlanningObserver` 参数 |
| 公共噪声与缓存工具已迁移 | 满足 | 见 3.3 |
| 数据包加载与注册表依赖已隔离 | 满足 | `config` 零 Minecraft import；`ContentPreflight` 本已通过 `RegistryLookup` 接口隔离，实现在 `AdventureEvents` |
| 输出基线一致 | 满足 | 每个提交上 `PlanningBaselineTest` 复现两个冻结哈希与 `decode→encode` 字节一致 |
| 测试全绿 | 满足 | 当时 161 项测试，0 失败（现已扩展到 164 项，见 [复现方式](#reproduce)） |

## 5．P2 结果

### 5.1 `244c1ac`／`cbfe4c2`／`eaf027c`：共享契约归位

经确认采用"按类型分别归位"：`PlannerProfile`、`PlanningFailure`、`StableIds` → `plan`，`DeterministicRandom` → `noise`。

这一次归位暴露出三个此前不可见的包环，必须一并打破，否则依赖方向仍然自相矛盾：

| 环 | 成因 | 处理 |
|---|---|---|
| `plan ↔ hydrology` | `PlannerProfile.V2` 读取 `RiverMorphology.VERSION` | 版本常量集中到 `plan.PlanVersions.HYDROLOGY`，`RiverMorphology.VERSION` 删除，方向改为 `hydrology → plan` |
| `plan ↔ spatial` | `spatial.AreaGrid` 读取 `PlannerProfile.V2.finalAreaCellSide()` | 网格权威归 `AreaGrid.CELL_SIDE`，`PlannerProfile.V2` 发布该值；`spatial` 现在零项目 import |
| `config ↔ plan` | `config.ContentPreflight` 需要 `PlanningFailure`，而 `plan` 需要 `config.ContentId` | `ContentId` 本身也是共享数据，随 `PlanningFailure`、`StableIds` 一起入 `plan` |

`planner` 也不再依赖 `terrain`（`GradientNoise` 随 `DeterministicRandom` 入 `noise`；`TerrainCapacityPlan` 的 `planner.*` 通配 import 改为显式 import，让真实依赖可见）。

### 5.2 `012152e`：容量求解与只读结果分离

`TerrainCapacityPlan` 曾同时是只读结果和需求求解器（`RequirementExpander`、山脉范围、贪心分箱、高度包络拟合），这正是 `terrain → planner` 的来源。

| 新位置 | 内容 |
|---|---|
| `planner.TerrainCapacitySolver` | `reserve()`、`Bin`／`Request`／`Choice`、`eligibleTemplates()` |
| `terrain.TerrainCapacityPlan` | 只读结果：`Reservation`、`Fit`、`reservations()`、`ranges()`、`at()`、`empty()` |

高度包络数学（`acceptsEnvelope`、`fit`、`erosionFactor`、`representative`）留在 `TerrainCapacityPlan`：旧版 `Reservation` 构造器需要它，而且它描述地形而非规划；求解器调用它，因此 `fit`／`acceptsEnvelope` 改为 public——这是唯一的可见性变化。

拆分做了机械化校验：把刻意改动的重命名（`Fit`／`Reservation` 限定名、字段访问器、`allowed` → `eligibleTemplates`）反向还原后，原文件的每一行代码都能在新文件之一中找到，无逻辑丢失或改写。

### 5.3 `efe9c76`：湿度供给修正显式化

`HumidityPlan.computeValue` 原本做两件事：算自然湿度场，然后把结果吸附到当前填充池在该模板/地貌下可用的湿度带。后者是真实耦合（换 `biomes.filler` 会移动环境场），但藏在场计算内部。

| 新位置 | 内容 |
|---|---|
| `planner.HumiditySupplyCorrection` | 可行带掩码、其缓存、吸附逻辑，并写明与填充池的耦合 |
| `HumidityPlan.naturalValue` | 自然湿度场，不含填充池知识 |
| `HumidityPlan.computeValue` | 自然值 → 非湿列才做修正 |

按规划要求**保留**该修正，未删除。同样做了逐行校验：7 行自然场计算与 19 行修正逻辑原样存在，湿列短路用等价三元表达式保留。

### 5.4 `3e64123`：无状态混合器归位

`PlacementIndex.mix` 是 SplitMix64 终混合，用于气候、填充、生长与联合放置的种子排序与抖动，本身不含任何放置状态。移入 `noise.DeterministicRandom.mix`，10 处调用点同步更新。这去掉了 `ClimatePlan` 仅有的两个 planner 依赖之一。

### 5.5 `01d9682`：群系过渡进入 `biome` 包

`terrain.LocalBiomeBlend` → `biome.LocalBiomeBlend`。地块归属过渡是群系职责，不是地形（高度、水位、材料）职责。新建的 `biome` 包只依赖 `plan` 与 `noise`，无环。

### 5.6 `PackageBoundaryTest` 扩展到 7 项

新增：`terrain` 不得依赖 `planner`／`runtime`（防止配额求解回流），`biome` 不得依赖 `planner`／`runtime`。

### 5.7 P2 未完成部分的前置耦合

规划 §4.1 要求把温湿度允许范围、权重评分、硬高度与海岸优先级集中为"群系环境规则服务"，供播种、扩张、填充、过渡共用；目标表把温度场/湿度场归 `climate`、准入与评分归 `biome`。实测到的实现顺序如下：

1. **`ClimatePlan` 仍有一个 planner 依赖**：`RequirementExpander`（用于需求比例与供给诊断）。规划 §4.1 把这件事本身列为交付项——"将供需统计、目标比例和日志整理为独立诊断结果"。做完它，`ClimatePlan` 才能进 `climate` 而不形成 `climate → planner` 环。
2. **诊断结果受线格式约束**：`ratios`／`actual`／`supply` 是 `ClimatePlan.State` 的扁平字段，而 `State` 由 `plan-v2` 的 `biome_layout` 直接 Gson 序列化。规划 §6.3 明确要求"提取数据类时保留现有线格式"，所以不能把它们改成嵌套对象；可用的做法是**计算**独立成诊断类、**存储**保持扁平字段，并把这一兼容取舍写清楚。
3. **准入与评分有约 35 处调用点**（`JointPlanner`、`BiomeAllocationPlanner`、`FillerLayout`、`GeneratedAdventurePlan` 及 6 个测试/测试驿站文件）。它们已全部经由 `allowsEnvironment`／`cost` 这同一套方法，所以"各阶段使用同一套准入规则"目前**已经成立**；待做的是把这套规则从字段类里搬出来成为具名服务。
4. 顺序建议：先做 (1) 诊断抽取，再把温度/湿度场类移入 `climate`，最后建 `biome.BiomeEnvironmentRules` 并改调用点。三步各自可独立编译、测试与提交。

## 6．当前依赖实测

`main` 源码包之间的实际 import 关系（仅列存在边的包）：

```text
.            -> config, plan, runtime, worldgen
api          -> plan
biome        -> noise, plan
client       -> runtime
config       -> api, plan
cost         -> api, plan, planner, spatial, terrain
erosion      -> api, hydrology, noise, plan
hydrology    -> api, noise, plan, spatial, terrain
mixin        -> worldgen
noise        -> spatial
persistence  -> api, config, erosion, hydrology, plan, runtime, spatial, terrain
plan         -> spatial
planner      -> api, config, biome, noise, plan, spatial, terrain
runtime      -> api, biome, config, cost, erosion, hydrology, noise, persistence, plan, planner, spatial, terrain
spatial      -> (无)
terrain      -> api, noise, plan, spatial
worldgen     -> api, config, hydrology, persistence, plan, runtime
```

P1 完成时（`6a70479`）实测有 **6 个包环**，现在只剩 **1 个**：

| P1 完成时的包环 | 消除于 |
|---|---|
| `api ↔ config` | P2.0c（`ContentId` → `plan`） |
| `api ↔ planner` | P2.0c（`PlanningFailure` → `plan`） |
| `config ↔ planner` | P2.0c（同上） |
| `planner ↔ spatial` | P2.0b（`AreaGrid` 自持网格常量） |
| `planner ↔ terrain` | P2.0a（`GradientNoise` → `noise`）、P2.1（求解器迁出 `terrain`） |
| `persistence ↔ runtime` | **仍存在**，属 P3 |

P2.0b／P2.0c 期间还短暂出现过 `plan ↔ hydrology`、`plan ↔ spatial`、`plan ↔ config`（移动单个类型时把环换了位置），都在同一提交内打破，见 [5.1](#p2)。

`spatial` 现在没有任何项目 import；`plan` 只依赖 `spatial`。

import Minecraft / NeoForge 的包只剩：根包（`AdventureWorldGen`、`AdventureEvents`）、`client`、`mixin`、`runtime`、`worldgen`。

### 7.1 共享契约类型归属：已决定并已实施

经确认采用"按类型分别归位"：`PlannerProfile`、`PlanningFailure`、`StableIds` → `plan`；`DeterministicRandom` → `noise`。实施中暴露的三个包环已一并打破，详见 [5.1](#p2)。本项**已完成**，不再是待办。

### 7.2 冻结环境状态提取（P3）

`ClimatePlan.State`、`HumidityPlan.State`、`FillerLayout.State`、`ClimatePlan.Correction`／`Supply`、`BiomeLayout` 仍定义在 `planner`／`runtime`。规划把"冻结环境状态"列为 `plan` 的职责。因涉及 `plan-v2` 中 `biome_layout` 的 Gson 反射序列化（字段名与嵌套结构必须逐字保持），建议与 7.4 的 `GeneratedAdventurePlan` 缩小一并在 P3 完成，并复用 `PlanningBaselineTest` 的往返断言作为守卫。

### 7.3 P2 剩余：环境与群系边界

### 7.4 P3：构建与恢复边界

- `persistence.PlanV2Codec` 仍直接依赖 `runtime.GeneratedAdventurePlan`（`decode` 返回它、`encode` 接收它），并读取其 `BiomeLayout`。规划要求"存储层只处理冻结数据"。
- `GeneratedAdventurePlan` 仍有 5 个构造器并在构造时组装地形、气候、填充、面积保护并初始化查询缓存。规划要求缩小它并区分首次规划与 READY 恢复两个入口。
- `RuntimePlanner` 同时承担阶段编排、输入身份计算与可选结构回退，边界可进一步收紧。

### 7.5 P4：结构适配贯通

- `worldgen.AdventureChunkGenerator` 恢复冻结部件时仍只接受 `minecraft:tedp`，并直接构造 `DesertPyramidPiece`（规划 §4.3 明确要求删除该分支，且不得以更长的结构 ID 分支替代）。
- `worldgen.VanillaDesertPyramidAdapter` 需移入原版兼容包。
- `api.StructureAdapter` 声明的 `serializePieces`、`placeChunk` 在生产路径未见调用，测试中仅 `placeChunk` 被调用；需明确迁移或废弃，不能同时承诺两套执行机制。
- 现有测试驿站复用了 `DesertPyramidPiece`，**不能证明**任意部件类型的恢复能力；P4 必须补一种真实异类部件类型，并覆盖规划 §6.2 的五项验收。

### 7.6 未运行的验证

- 本轮**未**运行游戏内 GameTest 与专用服务器验证（需要启动 Minecraft 运行时）。P4 涉及结构恢复与地表行为时必须追加。
- 本轮**未**做逐阶段性能对照。规划 §6.1 要求先测波动范围，再判定"超出波动的持续退化"。

### 7.7 遗留的小问题

- `runtime.RuntimePlanRegistry` 以 `net.minecraft.resources.ResourceLocation` 作为计划表的键，因此 `runtime` 仍 import Minecraft。它不做注册表查询（只是 map 键），不属于 P1.4 的"数据包加载与注册表依赖"，但若希望 `runtime` 完全不依赖 Minecraft，可改键为 `ContentId` 并在 `worldgen` 边界转换。
- `docs/设计原则.md` 与《配置说明》的 6 处冲突（见[重构基线 §5](重构基线.md#conflicts)）尚未在文档层解决。规划 §7 要求按变更记录、已确认决定与代码共同核对，不能仅凭代码现状自动决定产品语义。

## 8．复现方式

```bash
cd neoforge
./gradlew compileJava compileTestJava compileTestmodJava --offline --console=plain
./gradlew test --offline --no-build-cache --console=plain
```

`--no-build-cache` 不可省略：`:test` 可被 Gradle 构建缓存命中而直接返回 `FROM-CACHE`，那样并没有真正执行测试。基线对照见[重构基线 §2](重构基线.md#verify)。

当前结果：164 项测试（原 156 + 端到端计划字节基线 1 + 架构边界守卫 7），0 失败、0 错误、0 跳过。
