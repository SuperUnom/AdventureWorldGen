## 3．P1 结果

### 3.1 `842570f`：提取共享计划数据

`GeneratedAdventurePlan.PlannedBiomePatch` → `plan.PlannedBiomePatch`。

`planner` 产出该类型而 `runtime` 组装 planner 对象，`planner` 与 `runtime` 因此构成真实的包环。地块归属、边界与面积属于共享计划数据，移入 `plan` 后规划器不再 import 运行时计划类。记录的字段名与顺序未变，`PlanV2Codec` 按显式字段名读写，线格式不变。

### 3.2 `c67e360`：进度观察接口

新增 `plan.PlanningStage`（由 `PlanningProgress.Stage` 移动而来，常量名、区间与翻译键不变）与 `plan.PlanningObserver`（只有 `stage`／`detail`／`within` 三个方法，含 `NONE` 实现）。

`PlanningProgress.Run` 实现该接口，`RuntimePlanner` 把当前运行显式传给 `JointPlanner`、`ClimatePlan`、`FillerLayout` 与 `GeneratedAdventurePlan`。原先算法直接调用的静态 `stageCurrent`／`withinCurrent`／`detailCurrent` 全部删除。

结果：`planner` 不再 import `runtime`，这原是 P1 的出口条件。进度只作观察，仍不参与生成、重试或随机输入。

### 3.3 `db9512b`：迁移公共噪声与缓存工具

| 原位置 | 新位置 |
|---|---|
| `terrain.ValueNoise` | `noise.ValueNoise` |
| `terrain.ContinuousDomainWarp` | `noise.ContinuousDomainWarp` |
| `planner.CellMask` | `spatial.CellMask` |
| `runtime.ColumnQueryCache` | `spatial.ColumnQueryCache` |

对应测试随生产包迁移。纯位置调整：无方法、常量、数值或顺序改动。地形不再伸入 `runtime`，计划数据不再伸入 `planner`，`noise` 不依赖规划或运行时。

### 3.4 `6354506`：隔离数据包加载

`config.ProfileManager` 是 `config` 中唯一的 Minecraft 依赖（继承 `SimplePreparableReloadListener`、读取数据包资源）。按规划给 `config` 划定的边界拆开：

- `config.LoadedProfile`：纯结果数据（身份、已校验配置、规范化 JSON、输入哈希、来源包），无 Minecraft 类型。
- `worldgen.ProfileReloadListener`：持有资源栈、固定资源位置与当前 profile 注册表，产出 `LoadedProfile`。

`config` 现在零 Minecraft import；`RuntimePlanner` 改用 `LoadedProfile` 而非 reload listener 的嵌套类型。控制流、校验规则、错误码、冲突检测与规范化 JSON 身份均未改变。

### 3.5 `PackageBoundaryTest`：边界守卫

4 项源码级检查，防止后续改动悄悄恢复已移除的依赖：

| 检查 | 断言 |
|---|---|
| `configLayerHasNoMinecraftOrNeoForgeDependency` | `config` 不 import `net.minecraft` / `net.neoforged` |
| `planningAlgorithmsDoNotDependOnTheRuntimeLayer` | `planner` 不 import `...runtime` |
| `planDataDoesNotDependOnPlanningOrRuntime` | `plan` 不 import `...planner` / `...runtime` |
| `sharedNoiseToolsDoNotDependOnPlanningOrRuntime` | `noise` 不 import `...planner` / `...runtime` |

已人工验证其有效性：向 `planner/StableIds.java` 注入一行 `...runtime.RuntimePlanner` 的 import 后，`planningAlgorithmsDoNotDependOnTheRuntimeLayer` 立即失败；移除注入后恢复通过。

## 4．P1 出口条件核对

《重构规划》对 P1 的出口要求是"算法不依赖具体运行时数据类或静态界面进度；输出基线一致"。

| 要求 | 结论 | 证据 |
|---|---|---|
| 算法不依赖具体运行时数据类 | 满足 | `planner` 无 `...runtime` import；由 `PackageBoundaryTest` 守护 |
| 算法不依赖静态界面进度 | 满足 | 静态 `stageCurrent`／`withinCurrent`／`detailCurrent` 已删除；改为显式 `PlanningObserver` 参数 |
| 公共噪声与缓存工具已迁移 | 满足 | 见 3.3 |
| 数据包加载与注册表依赖已隔离 | 满足 | `config` 零 Minecraft import；`ContentPreflight` 本已通过 `RegistryLookup` 接口隔离，实现在 `AdventureEvents` |
| 输出基线一致 | 满足 | 每个提交上 `PlanningBaselineTest` 复现两个冻结哈希与 `decode→encode` 字节一致 |
| 测试全绿 | 满足 | 当时 161 项测试，0 失败（现已扩展到 171 项，见 [复现方式](#reproduce)） |

## 5．P2 结果

### 5.1 `244c1ac`／`cbfe4c2`／`eaf027c`：共享契约归位

经确认采用"按类型分别归位"：`PlannerProfile`、`PlanningFailure`、`StableIds` → `plan`，`DeterministicRandom` → `noise`。

这一次归位暴露出三个此前不可见的包环，必须一并打破，否则依赖方向仍然自相矛盾：

| 环 | 成因 | 处理 |
|---|---|---|
| `plan ↔ hydrology` | `PlannerProfile.V2` 读取 `RiverMorphology.VERSION` | 版本常量集中到 `plan.PlanVersions.HYDROLOGY`，`RiverMorphology.VERSION` 删除，方向改为 `hydrology → plan` |
| `plan ↔ spatial` | `spatial.AreaGrid` 读取 `PlannerProfile.V2.finalAreaCellSide()` | 网格权威归 `AreaGrid.CELL_SIDE`，`PlannerProfile.V2` 发布该值；`spatial` 现在零项目 import |
| `config ↔ plan` | `config.ContentPreflight` 需要 `PlanningFailure`，而 `plan` 需要 `config.ContentId` | `ContentId` 本身也是共享数据，随 `PlanningFailure`、`StableIds` 一起入 `plan` |

`planner` 也不再依赖 `terrain`（`GradientNoise` 随 `DeterministicRandom` 入 `noise`；`TerrainCapacityPlan` 的 `planner.*` 通配 import 改为显式 import，让真实依赖可见）。

### 5.2 `012152e`：容量求解与只读结果分离

`TerrainCapacityPlan` 曾同时是只读结果和需求求解器（`RequirementExpander`、山脉范围、贪心分箱、高度包络拟合），这正是 `terrain → planner` 的来源。

| 新位置 | 内容 |
|---|---|
| `planner.TerrainCapacitySolver` | `reserve()`、`Bin`／`Request`／`Choice`、`eligibleTemplates()` |
| `terrain.TerrainCapacityPlan` | 只读结果：`Reservation`、`Fit`、`reservations()`、`ranges()`、`at()`、`empty()` |

高度包络数学（`acceptsEnvelope`、`fit`、`erosionFactor`、`representative`）留在 `TerrainCapacityPlan`：旧版 `Reservation` 构造器需要它，而且它描述地形而非规划；求解器调用它，因此 `fit`／`acceptsEnvelope` 改为 public——这是唯一的可见性变化。

拆分做了机械化校验：把刻意改动的重命名（`Fit`／`Reservation` 限定名、字段访问器、`allowed` → `eligibleTemplates`）反向还原后，原文件的每一行代码都能在新文件之一中找到，无逻辑丢失或改写。

### 5.3 `efe9c76`：湿度供给修正显式化

`HumidityPlan.computeValue` 原本做两件事：算自然湿度场，然后把结果吸附到当前填充池在该模板/地貌下可用的湿度带。后者是真实耦合（换 `biomes.filler` 会移动环境场），但藏在场计算内部。

| 新位置 | 内容 |
|---|---|
| `planner.HumiditySupplyCorrection` | 可行带掩码、其缓存、吸附逻辑，并写明与填充池的耦合 |
| `HumidityPlan.naturalValue` | 自然湿度场，不含填充池知识 |
| `HumidityPlan.computeValue` | 自然值 → 非湿列才做修正 |

按规划要求**保留**该修正，未删除。同样做了逐行校验：7 行自然场计算与 19 行修正逻辑原样存在，湿列短路用等价三元表达式保留。

### 5.4 `3e64123`：无状态混合器归位

`PlacementIndex.mix` 是 SplitMix64 终混合，用于气候、填充、生长与联合放置的种子排序与抖动，本身不含任何放置状态。移入 `noise.DeterministicRandom.mix`，10 处调用点同步更新。这去掉了 `ClimatePlan` 仅有的两个 planner 依赖之一。

### 5.5 `01d9682`：群系过渡进入 `biome` 包

`terrain.LocalBiomeBlend` → `biome.LocalBiomeBlend`。地块归属过渡是群系职责，不是地形（高度、水位、材料）职责。新建的 `biome` 包只依赖 `plan` 与 `noise`，无环。

### 5.6 `505a6d5`：诊断统计独立化

`ClimatePlan` 原本内联计算需求比例、实际温度带分布与逐需求供给统计，并使用 `RequirementExpander`。这些是诊断数据（代码已注明它们从不改写温度场），但与场构建纠缠在一起。

| 新位置 | 内容 |
|---|---|
| `planner.ClimateDiagnostics` | `targetRatios`／`actualRatios`／`supply` 与 `distribute`／`preferredBiome`／`climateArea` |
| `planner.ClimateDiagnostics.Site`／`Supply` | 采样点与持久化供给条目（各一份定义） |
| `planner.ClimateDiagnostics.TemperatureField` | 统计所需的两个温度观察（带序数、未阈值化取值） |

`ClimatePlan` 仍在原位记录这三项统计，因此**持久化形状未变**：`State` 保持扁平的 `ratios`/`actual`/`supply` 组件，因为 `plan-v2` 反射序列化 `biome_layout`，而规划 §6.3 要求保留现有线格式——所以数据保持扁平、计算独立成单元。`ClimatePlan` 也不再引用 `RequirementExpander`。新增 `ClimateDiagnosticsTest` 用合成站点与合成温度场独立验证统计，期望值直接写出而非抄自生产输出。

### 5.7 `dd6180a`：准入与评分成为唯一共享服务

`ClimatePlan` 曾混合冻结温度场与使用该场的规则：群系可占温度带、湿度准入、`shore_only`、海岸优先、硬高度成本与偏好评分。播种、生长、填充与过渡各自向温度场索取这些答案。

| 新位置 | 内容 |
|---|---|
| `planner.BiomeEnvironmentRules` | `allows`／`prefersType`／`temperatureDistance`／`cost`，静态 `preferences`／`weight`，以及原先挂在温度场上的海岸优先填充列表 |
| `ClimatePlan` | 只保留温度场、湿度场与其持久化状态 |

`JointPlanner`、`BiomeAllocationPlanner`、`FillerLayout`、`GeneratedAdventurePlan` 以及测试与测试驿站全部改为经由该服务判定归属。服务不持有搜索状态，只读冻结输入。每个搬移的方法体都与搬迁前源码做过 token 级逐字比对，全部一致。新增 `BiomeEnvironmentRulesTest` 固定了这次统一所要保证的性质，其中一条澄清了实现细节：**准入判定发生在最终 4 格归属网格中心，而非原始坐标**。

### 5.8 `524e6b1`：地表材料与 `api` 去实现化

修正后的依赖扫描（见 §8 的方法更正）发现 `api → hydrology`，构成真实的 `api ↔ hydrology` 环，成因正是规划两处点名的内容：`hydrology.RiverSediments` 直接选择原版方块调色板（§4.1），`api.GenericBiomeAdapter` 是住在契约包里的内置实现（目标表禁止）。

| 原位置 | 新位置 |
|---|---|
| `hydrology.RiverSediments` | `surface.RiverSediments` |
| `api.GenericBiomeAdapter` | `worldgen.GenericBiomeAdapter` |

`surface` 现在只依赖 `api`／`noise`／`plan`；`api` 只依赖 `plan`，不再牵入任何领域或执行层代码。该环消除。

### 5.9 `PackageBoundaryTest` 扩展到 8 项

新增：`terrain` 不得依赖 `planner`／`runtime`；`biome` 不得依赖 `planner`／`runtime`；`surface` 不得依赖 `hydrology`／`planner`／`runtime`／`worldgen`；`api` 不得依赖 `planner`／`runtime`／`hydrology`／`terrain`／`surface`／`worldgen`。

同时修正了守卫本身的方法缺陷：它此前只看 `import` 行，因此内联完全限定名可以绕过它——这正是 `api → hydrology` 长期未被发现的原因。现在它会去除注释并扫描整个文件（允许 `package` 声明行）。

### 5.10 P2 未完成部分的前置耦合（历史记录，结论见 [5.7](#p2)）

规划 §4.1 要求把温湿度允许范围、权重评分、硬高度与海岸优先级集中为"群系环境规则服务"，供播种、扩张、填充、过渡共用；目标表把温度场/湿度场归 `climate`、准入与评分归 `biome`。实测到的实现顺序如下：

1. **`ClimatePlan` 仍有一个 planner 依赖**：`RequirementExpander`（用于需求比例与供给诊断）。规划 §4.1 把这件事本身列为交付项——"将供需统计、目标比例和日志整理为独立诊断结果"。做完它，`ClimatePlan` 才能进 `climate` 而不形成 `climate → planner` 环。
2. **诊断结果受线格式约束**：`ratios`／`actual`／`supply` 是 `ClimatePlan.State` 的扁平字段，而 `State` 由 `plan-v2` 的 `biome_layout` 直接 Gson 序列化。规划 §6.3 明确要求"提取数据类时保留现有线格式"，所以不能把它们改成嵌套对象；可用的做法是**计算**独立成诊断类、**存储**保持扁平字段，并把这一兼容取舍写清楚。
3. **准入与评分有约 35 处调用点**（`JointPlanner`、`BiomeAllocationPlanner`、`FillerLayout`、`GeneratedAdventurePlan` 及 6 个测试/测试驿站文件）。它们已全部经由 `allowsEnvironment`／`cost` 这同一套方法，所以"各阶段使用同一套准入规则"目前**已经成立**；待做的是把这套规则从字段类里搬出来成为具名服务。
4. 顺序建议：先做 (1) 诊断抽取，再把温度/湿度场类移入 `climate`，最后建 `biome.BiomeEnvironmentRules` 并改调用点。三步各自可独立编译、测试与提交。

### 6.2 `1788158`：存储层只处理冻结数据

`persistence.PlanV2Codec` 原先以 `runtime.GeneratedAdventurePlan` 为契约（`decode` 返回它、`encode` 接收它、并读取其 `BiomeLayout`），而 `runtime` 又使用该编解码器，构成 `persistence ↔ runtime` 包环。现在：

| 位置 | 内容 |
|---|---|
| `persistence.PlanSnapshot` | 一份 `plan-v2` 文档冻结的全部数据：种子、诊断计数、出生点、海岸线、河网、水面/陆带/海带、地形版本、recipe 设置与区域清单、地块、结构、侵蚀场、容量结果、`plan.BiomeLayout` |
| `plan.PlanDiagnostics` | `operation_counts` 段的数据；`basic(...)` 改为只接收计数与版本字符串，不再需要 `terrain`／`hydrology` 类型 |
| `persistence.PlanV2Codec` | `encode(profile, inputHash, snapshot)`、`decode(bytes, profile, inputHash) → PlanSnapshot`；不再 import `runtime`，也不再需要 `config` |
| `runtime.GeneratedAdventurePlan` | `snapshot()` 发布首次规划的冻结数据；`restore(config, snapshot)` 由冻结数据重建查询对象 |

`recipe_settings` 与 `recipe_regions` 现在从**载荷读回**并进入快照，不再由当前 profile 重新生成；因此 READY 重载后的再次编码与原始字节一致，不再依赖"当前配置恰好未变"。这两项与实时 profile 的交叉校验（冻结 recipe 设置、冻结区域清单）随实时配置一起移入 `restore`：`restore` 先按快照组装，再依次校验，失败仍是 `PlanningFailure`／`EXECUTION_FAILED`／`plan-load`，与搬迁前的错误码和 `reason` 文本一致。区域清单校验由"重新序列化后与 JSON 树比较"改为"记录相等"，语义是内容而非字节；线格式未变。

`PlanSnapshot` 放在 `persistence` 而不是 `plan`：它引用 `Coastline`、`RiverNetwork`、`ErosionDeltaField`、`TerrainCapacityPlan`，而这些包已经依赖 `plan`，放进 `plan` 立即成环。存储层是已经看得到全部领域的最低层，冻结快照因此归它；冻结**环境状态**（`plan.BiomeLayout`）仍在 `plan`。

`PackageBoundaryTest` 新增 `storageLayerOnlyHandlesFrozenData`（`persistence` 不得 import `runtime`）。按既有做法人工验证：向 `persistence/PlanV2Codec.java` 注入一行 `runtime` import 后该测试立即失败，移除后恢复通过。

### 6.4 两路径的缓存差异：已接受的优化策略

**已确认决定**（用户确认）：统一地形公式与组装入口，**保留**两路径的缓存差异，并把它明确为已接受的优化策略，不再作为待决项。

代码现状：

| 事项 | 状态 |
|---|---|
| 地形公式与组装入口 | 统一：两路径都经 `PlanTerrain` 组装（regions → island → erosion → hydrology → morphology），`PlanAssembly` 与 `restore` 走同一组合 |
| 查询语义 | 统一：同一坐标在两条路径上得到相同采样 |
| 首次规划的额外缓存 | 保留 `PlanTerrain.withMemoizedQueries()` 给出的 `ExactGridTerrain`（半格/整格记忆化，容量 262144） |
| READY 恢复 | 只给纯 `TerrainMorphology`，不额外创建同规模缓存 |
| 两条路径都有的缓存 | `GeneratedAdventurePlan` 无论哪条路径都创建容量 16384 的 `columnSamples` 与 `columnBiomes`；差异只在首次规划额外保留那一份 262144 的包装 |

依据：

1. **正确性已统一**：两路径共用 `PlanTerrain`；`PlanV2CodecTest` 覆盖首次构建与恢复的查询结果对照，`PlanTerrainTest` 固定"缓存不改变采样"（含离格坐标不被量化）。
2. **首次规划保留缓存有明确用途**：复用规划阶段已采样的结果，供后续装配、终检与运行时查询使用；直接移除会失去这项复用。
3. **恢复路径增加同规模缓存的收益不足以支持改动**：现有测量只是特定负载下的约 10.9 MB 保留堆与约 1.2× 采样吞吐，不能推导为游戏整体性能提升。
4. **恢复路径并非没有缓存**：两条路径都带 16384 的列采样缓存，差别只是首次规划额外保留 262144 的那一份。

测量记录（半径 512、同一配置与查询负载；临时测量代码已删除；3 次重复，`System.gc()` 后取堆用量。保留作为该策略的依据，**不作为性能验收**）：

| 指标 | 纯 `TerrainMorphology` | 记忆化包装 | 差值 |
|---|---|---|---|
| 保留堆（3 次） | 11.73／11.66／11.78 MB | 22.63／22.57／22.73 MB | **+10.9 MB**（10.89／10.91／10.95，稳定） |
| 729 列查询负载 | 8–9 ms | 7 ms | 约 1.2× 吞吐 |

**何时重开**：若游戏侧对照显示恢复路径的区块查询因缺少该缓存而显著偏慢，再按规划 §6.1 的流程评估为恢复路径加缓存，届时仍以同机对照为准。

**这不等于性能验收**：P3 出口的"性能无未解释退化"由独立的同机对照完成，见 [6.7](#p3-performance)。

### 6.5 `1f78d48`…`ed8ee42`：计划构建职责具名化

`GeneratedAdventurePlan` 的构造器此前自己做地形、气候、填充、出生点与面积保护的组装。现在组装分别归入具名单元，计划对象只留下"需要它自己的查询"的两步：

| 新位置 | 内容 | 单元 |
|---|---|---|
| `runtime.PlanTerrain` | 地形栈组装（regions → island → erosion → hydrology → morphology），以及被显式命名的记忆化查询包装 | `1f78d48` |
| `planner.MinimumAreaPolicy` | 最小面积策略：混合前必须保护的补丁集合，与装配后的面积终检 | `2786282` |
| `runtime.PlanAssembly` | 气候场、环境规则、填充网格的组装（"冻结或新建"、阶段通知与复用规则），以及出生点解析 | `dbc565c` |
| `GeneratedAdventurePlan` | 只保留：无冻结出生点时由已组装地形解析出生点、以及需要计划自身查询的最小面积测量 | `dbc565c` |

三点说明：

1. **`PlanTerrain` 就是规划要求的"统一地形组装工厂"**：首次规划把自己已经建好的对象交进来（保留复用优化），READY 恢复用冻结数据重建同一栈。两路径唯一保留的差异被显式命名为 `withMemoizedQueries()`，其取舍已确认保留，见 [6.4](#p3-assembly)。
2. **`MinimumAreaPolicy` 让"保护"与"终检"共用同一次比较**：`protectedPatchIds(...)` 决定哪些补丁不能被过渡缩小，`checkAchievedAreas(...)` 在装配后复核并把接受的放宽逐个交给调用方。日志与失败文本仍留在 `runtime`，失败码、`stage` 与诊断字段与搬迁前逐项一致；失败时只报告失败之前的放宽。新增 `MinimumAreaPolicyTest`（4 项）固定该顺序与两条分支。
3. **`PlanAssembly` 集中了"冻结还是新建"**、`FILLER`/`TRANSITION` 阶段通知，以及"首次规划复用联合放置已建的气候场"这条复用规则。
4. **指标边界**：编排器只用自己的阶段枚举调用 `PlanningMetrics.finish(Stage)`（键字符串保持不变，`planning-metrics.json` 内容不变），联合放置的报告检查点仍按名称汇入同一时间线；指标类本身只写诊断，不进入计划字节、输入身份或任何随机输入。
5. **首次规划入口（`9a3c8cd`）**：底层完整构造器是 **17 参**（本文早前写作"16 参"有误）；具名入口 `fromPlanning(...)` 隐藏 `frozenLayout` 后为 **16 参**，并在内部要求复用对象非空。该构造器已改为私有，编排器与首次规划基线测试都改走 `fromPlanning(...)`；公共兼容构造器（9／13／14／15 参）保留，供测试与只读工具从显式几何构建计划。

行为未变：上述每个提交都复现冻结 `plan-v2` 字节与采样字段哈希，全套测试从 178 增至 182 项（新增 4 项策略测试），0 失败。

## 7．P4 结果

P4 的目标是让"支持一种结构"变成一次注册，而不是通用生成器里的分支（规划 §4.3）。本轮完成两个迁移单元：冻结部件的恢复改走部件注册表，原版专用适配器迁出核心包。

### 7.1 `bb15981`：冻结部件按注册部件类型恢复

原实现：`AdventureChunkGenerator.createStructures` 解出冻结 NBT 后比较 `id` 是否等于 `minecraft:tedp`，相等才 `new DesertPyramidPiece(tag)`，其他类型一律抛"unsupported frozen piece type"。新增一种结构就必须修改通用生成器。

现实现：新增 [FrozenPieceRestore](../neoforge/src/main/java/io/github/luoyan/adventureworldgen/worldgen/FrozenPieceRestore.java)，用冻结 NBT 的 `id` 在 `BuiltInRegistries.STRUCTURE_PIECE` 中查到注册的 `StructurePieceType`，交给该类型自己重建部件。这正是原版 `PiecesContainer.load`（以及 `StructureStart.loadStaticStart`）使用的机制，恢复因此对"生成器从未听说过的结构"同样成立。生成器里不再出现任何结构 ID 或部件类。

与原版容器加载器刻意的三处语义差异：

| 方面 | 原版 `PiecesContainer.load` | 本实现 |
|---|---|---|

| 旧版部件重命名表（`nvi`／`pcp`／`bastionremnant`／`runtime` → `jigsaw`） | 应用 | 不应用 |

理由：已保存的区块必须能加载，原版只能丢弃；已发布的计划是承诺，缺部件应当尽早、点名失败（规划 §4.3、§6.2.5）。冻结 id 由适配器用 `createTag` 写入，只能是规范注册键，出现别的 id 说明计划与当前注册不一致，此时"变成别的东西"比失败更危险。

### 7.5 `5306e5a`（破坏性）：删除未接通的放置接口

规划 §4.3 要求对无生产调用的 `serializePieces`、`placeChunk` 明确去向，§6.3 要求公开接口的破坏性调整先出影响清单。**用户已确认：保留"冻结 NBT → 注册表恢复 → `StructureStart` 原生生成"这一条执行路径，不接通第二套放置机制**，因此在一个单独的破坏性提交中直接删除。

不接通旧接口的理由：

1. `serializePieces` 只是把已有的 `canonicalNbt()` 拼接起来，没有长度、边界或版本协议，不能构成可靠的存储格式。
2. `PlacementTarget` 只有 `beginOnce` 与 `placeCanonicalPiece`，无法表达 `postProcess` 需要的世界、随机源、结构管理器、地块包围盒与引用语义。
3. 接通 `placeChunk` 会与 Minecraft 的 `StructureStart.placeInChunk` 形成两套放置／幂等机制，容易重复生成或漏掉引用。

影响清单与落实：

| 范围 | 影响 | 处理 |
|---|---|---|
| 公开接口 | `api.StructureAdapter` 的两个方法与嵌套 `PlacementTarget` | 删除；接口到 `validatePrepared` 为止，javadoc 写明只有一条执行路径 |
| 生产实现 | `compat.vanilla.VanillaDesertPyramidAdapter` 中两个无生产作用的实现 | 删除 |
| 伴生模组 | `testcompanion.TestCompanionAdapters` 的相应实现 | 删除 |
| 测试 | `StructureAdapterBridgeTest` 的桩；模拟 `placeChunk` 的 GameTest | 删除桩；该 GameTest 改名 `externalAdaptersPreserveSurfaceVegetationAndFrozenLoot`，只保留冻结证据（跨区块部件覆盖、冻结战利品表） |
| 工具 | `tools/PlanningBenchmark` 的两个桩 | 删除 |
| 第三方源码 | 带 `@Override` 的旧实现重新编译失败 | 破坏性提交。`0.1.0` 无 tag、无发布产物，仓库内无第三方实现，按"尚无外部适配器使用者"处理 |
| 第三方二进制 | 旧适配器类仍可加载，但调用被删方法的代码 `NoSuchMethodError` | 不承诺二进制兼容 |
| 存档 | `plan-v2` 与 `PlannedPiece.canonicalNbt()` 未变 | 无需升级格式，生产 READY 不失效 |

文档同步：`docs/运行时与结构适配.md` 的第 1.2 节与第 2.2 节改写为唯一执行路径（适配器不再有逐区块提交入口，幂等来自冻结计划加原版区块流水线）；`docs/历史版本/plan-v1.md` 保留原描述并加历史标注；`Descriptor` 不列部件类型，冻结 NBT 的 `id` 是唯一事实来源。

186 项单元测试通过；`grep` 全仓确认代码中已无 `serializePieces`／`placeChunk`／`PlacementTarget` 引用。

### 9.7 游戏内验证与性能对照

**环境可以运行，此前记录里的说法有误。** 本机为 Java 21（Temurin 21.0.12）、31 GiB 内存、12 核；`neoforge/build.gradle` 已配置 `gameTestServer`；仓库中留有历次运行目录与日志，最近一次全绿为 2026-09-08 18:53（9 项 GameTest 全部通过，耗时 5.93 分钟）。"需要启动 Minecraft 运行时"是沿用旧结论，不是环境限制；2026-09-10 已在本机实际运行。

**2026-09-10 补跑结果（当前 HEAD 与重构前 `dd52875`）**：两次运行都在**全新游戏目录**中进行、日志中 `loading READY` 均为 0 次，因此都是全新规划结果：

| 运行对象 | 结果 | 失败项 |
|---|---|---|
| 当前 HEAD（含 P1–P3 重构） | 11 项中 4 项失败 | `productionProfilePlansIrregularContinentAtRadius3000`、`crashSeedPlansEveryRequiredBiome`、`constrainedCoastStillPlansAllRequiredBiomes`、`reportedSeedHasContainedDescendingRivers` |
| 重构前 `dd52875`（r29/r33 状态） | 11 项中 4 项失败，**完全相同的 4 项** | 同上 |

两次失败信息一致：`required biome lost its main contiguous body: minecraft:birch_forest / flower_forest / forest`，即 `AdventureWorldGameTests.assertTerrainBiomes` 的 `largestComponentArea(patch) == area` 断言。

**原因（已核对代码与文档，非本次重构引入）**：r29 已按用户确认把语义改为"同一需求使用一个稀疏归属集合，**允许包含多个不相连区域，面积合计**"，而该游戏内断言仍要求单一连通体；r29 自己的记录写明该轮"没有启动游戏、运行多种子批量测试或完整测试套件"。因此这 4 项自 2026-09-09 起即为红色，P1–P3 重构只是继承了这个状态。

**已确认（用户决定）**：这是**测试判断没有随 r29 更新**，不是规划器缺陷；更新测试判断即可（`bdb9fd2`）。`AdventureWorldGameTests.assertTerrainBiomes` 现在断言设计真正承诺的东西：

| 原断言 | 现断言 | 理由 |
|---|---|---|
| 需求必须有补丁（`orElseThrow`） | 允许缺席，但仅在**计划自身的供给记录**中该群系 `climateArea == 0` 时 | r29"完全没有合法位置时记录零供给并允许缺席"；仍防止"有合法空间却静默消失" |
| `area >= min && area <= max` | `area <= max`；混合后 `effectiveArea >= min(min, patch.area())` | r29 接受实际面积，`max` 保持硬上限；混合下限与规划器 `MinimumAreaPolicy` 的终检是同一比较 |
| `largestComponentArea(patch) == area`（单一连通体） | `sum(componentAreas(patch)) == area` | 多连通体合计合法；仍把归属集合与记录面积绑在一起 |

`largestComponentArea` 改名为 `componentAreas`，洪泛口径不变（4×4 方块单元、四邻接、不含对角），并在 javadoc 里写明 r29 语义。

**修复后运行（2026-09-10 20:11–20:18）**：全新目录 `run-verify-r29-assertions`（预置 `disableConfigWatcher = true`），**11 项 GameTest 全部通过，耗时 6.87 分钟**；5 次首次规划 12.3–128.5 秒；日志中的 2 次 READY 命中来自测试自身第二次 `plan()` 调用（重载校验），两项重载断言同样通过。

### 9.8 遗留的小问题

- `runtime.RuntimePlanRegistry` 以 `net.minecraft.resources.ResourceLocation` 作为计划表的键，因此 `runtime` 仍 import Minecraft。它不做注册表查询（只是 map 键），不属于 P1.4 的"数据包加载与注册表依赖"，但若希望 `runtime` 完全不依赖 Minecraft，可改键为 `ContentId` 并在 `worldgen` 边界转换。
- `docs/设计原则.md` 与《配置说明》的 6 处冲突（见[重构基线 §5](重构基线.md#conflicts)）尚未在文档层解决。规划 §7 要求按变更记录、已确认决定与代码共同核对，不能仅凭代码现状自动决定产品语义。

## 10．复现方式

```bash
cd neoforge
./gradlew compileJava compileTestJava compileTestmodJava --offline --console=plain
./gradlew test --offline --no-build-cache --console=plain
```

`--no-build-cache` 不可省略：`:test` 可被 Gradle 构建缓存命中而直接返回 `FROM-CACHE`，那样并没有真正执行测试。基线对照见[重构基线 §2](重构基线.md#verify)。

游戏内验证（全新游戏目录，避免读到旧 READY 计划；目录内 `config/fml.toml` 建议预置 `disableConfigWatcher = true`）：

```bash
./gradlew runGameTestServer -I tools/fresh-gametest-dir.gradle -PverifyWorld=run-verify --offline
```

`tools/fresh-gametest-dir.gradle` 只做一件事：把 `neoForge.runs.gameTestServer.gameDirectory` 指向 `-PverifyWorld` 指定的新目录（`tools/r24-gametest.gradle` 是同类脚本，另把命名空间收窄到 `testcompanion_planning`）。默认的 `gameTestServer` 运行带 `minecraft,adventureworldgen,testcompanion` 三个命名空间，当前共 13 项测试。

性能验收（[6.7](#p3-performance) 用的就是这三条，`-Xmx2g` 与 `dd52875` 对照一致）：

```bash
./gradlew -I tools/planning-benchmark.gradle writePlanningBenchmarkClasspath --offline
CP=$(cat build/planning-benchmark-classpath.txt)
PROFILE=src/main/resources/data/adventureworldgen/adventureworldgen/profiles/default.json
/usr/bin/time -v java -Xmx2g -cp "$CP" tools/PlanningBenchmark.java     "$PROFILE" build/bench-planning 7331
/usr/bin/time -v java -Xmx2g -cp "$CP" tools/PlanReloadBenchmark.java   build/bench-planning/adventureworldgen/plans/adventureworldgen_default "$PROFILE" 3
/usr/bin/time -v java -Xmx2g -cp "$CP" tools/ChunkQueryBenchmark.java   build/bench-planning/adventureworldgen/plans/adventureworldgen_default "$PROFILE"
```

`PlanningBenchmark` 要求输出目录不存在（否则会命中 READY 缓存，计时不可比）；重载与区块查询直接读已发布的 `plan.json.gz`。

当前结果：186 项测试（P2 完成时 171 项 + P3.0b 架构守卫 1 项 + P3.1 身份/结构桥接 6 项 + P3.2b 最小面积策略 4 项 + P3.3 地形栈不变量 3 项 + P4.1 部件恢复守卫 1 项），0 失败、0 错误、0 跳过；游戏内 13 项通过（见 [7.3](#p4) 与 [9.7](#next)）。
