## 2．逐项解决方案

### 01．`surface` 包不存在

依据：[目标职责表](重构规划.md)、[PackageBoundaryTest](../../neoforge/src/test/java/io/github/luoyan/adventureworldgen/PackageBoundaryTest.java)、[AdventureChunkGenerator](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/worldgen/AdventureChunkGenerator.java) 的 `buildPlannedSurface`。

方案：在重构规划中把 `surface` 明确标为“预留职责，当前由原版 surfaceRule 执行，无独立包”。从当前必须存在的包规则中移除该包，保留现有水文/侵蚀不得依赖方块选材的约束。以后有实际材料策略代码时再建立包和相应规则，不为测试创建空包。

验收：架构测试无因缺包产生的跳过；现有 SurfaceGameTests 仍覆盖真实表面流程。仅职责说明与测试规则调整，不更改材料或生成结果。

### 02．架构护栏依赖工作目录并静默跳过

方案：在 [build.gradle](../../neoforge/build.gradle) 的 `test` 任务中注入绝对源码根路径，`PackageBoundaryTest` 从该属性读取。路径缺失、应存在的包为空或关键文件缺失一律断言失败，替换当前用于环境检查的 `assumeTrue`。可选职责与必需包名单显式分开，先完成第 01 项。

验收：分别在工程目录、仓库根通过 `-p neoforge`、外部目录通过绝对 `-p` 路径执行同一测试，执行数量一致且 skipped=0；传入不存在的源码根时明确失败；临时引入一条禁止依赖时规则确实报错，随后恢复。规则数量以调整后的清单为准，不强求保留旧的 14 条。

### 03．默认 GameTest 不覆盖全部方法

方案：保留日常快速入口，新增明确的“完整验收”入口，依次启动默认、performance、capacity、planning 四组，各用独立世界目录，汇总任一失败为整体失败。现有 init 脚本会覆盖同一命名空间属性，**不能在一次启动中叠加三个 `-I` 来表示全量**。在工程 README 和验收指南列出每组范围与命令。

验收：按方法标识核对注册/发现/执行/通过/跳过数量；本基线应覆盖 16+6+1+1=24 个方法，方法数变化时更新清单。首次规划组使用全新目录；READY 专项单独复用同一目录。性能测试完成不等于性能达标，另报告耗时和峰值内存。

### 04．`LoadedProfile.configHash` 只写不读

依据：[LoadedProfile](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/config/LoadedProfile.java)、[PlanIdentity](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/runtime/PlanIdentity.java)。

方案：默认删除冗余字段及加载时的独立计算，继续以 `canonicalJson` 和生产身份组合生成 `input_sha256`，不把输入替换成“配置哈希的哈希”。删除前核对仓库外公开承诺；若已对外发布该构造器，则先弃用并提供保持源码兼容的过渡入口。

验收：同配置的规范 JSON、完整输入哈希及计划字节与基线一致；构造调用全部更新。配置单独摘要若将来确有日志需求，再按需计算，不维护第二份可能失配的身份状态。

### 05．`ResolvedContent` 返回值被丢弃

依据：[ContentPreflight](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/config/ContentPreflight.java) 的 `validate`。

方案：把预检明确为“验证成功返回、失败抛异常”的 `void` 方法，删除无人消费的 `ResolvedContent` 和返回时的列表复制。保留注册表解析、适配器存在性及可冻结能力检查，不为消化返回值另建一套内容状态。公开接口的过渡处理同第 04 项。

验收：合法配置继续成功，缺失群系/结构及不能冻结的适配器仍在同一预检阶段抛相同失败码和内容 ID，规划身份不变。

### 06．`random_keys` 与真实随机阶段名称不同

依据：[PlanV2Codec](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/persistence/PlanV2Codec.java) 的 `encode/decode`。

方案分两步。先将现有 `plan-v2.random_keys` 明确标为历史说明元数据，不宣称它参与恢复或证明随机调用完整性；保持原字段、顺序和解码行为，避免一次清理暗改线格式。随后集中实际随机阶段常量，逐个从调用点提取，**保留每个字符串原值、盐值、参数次序和调用顺序**。清单还要覆盖直接混种和噪声域名，不能只扫描一种随机函数。

需要可校验元数据时，在单独的协议变更中定义版本化随机域目录，由同一常量源导出；明确缺项、重复、未知项及旧载荷的处理策略。不能让新严格校验直接拒绝当前编码器曾生成的合法载荷。

验收：第一步黄金输出及 READY 往返字节不变；后续协议变更分别验证旧格式约定、新格式 round-trip 和损坏清单诊断。元数据一致只证明声明一致，确定性仍以重复规划和不同访问顺序验证。

### 07．测试夹具的地形版本串不统一

方案：生产语义测试统一从版本契约和测试工厂构造快照；历史回归夹具保留原版本，并在名称、注释及报告中标出历史目标。`terrain-v2`、`test` 等合成标记只能用于明确的合成对象。把散落的生产地形/侵蚀身份逐步集中，字符串值保持不变。

验收：每份黄金值能追溯提交、配置、种子与版本组合；夹具统一若改变规范字节，单独说明元数据差异，不能批量刷新所有哈希。生产版本覆盖和历史算法覆盖分别报告。

验收：索引链接唯一、目标存在，本文和原问题可相互定位；无需代码测试。

验收：读者可明确知道默认入口只覆盖哪组；没有执行的套件不能写“已通过”。新增测试后不要求修改历史计数。

### 10．25 个工具程序缺少复现入口

方案：新增 `neoforge/tools/README.md`，按每个带 `main` 的程序列出用途、主类、参数/默认值、输入资源、JDK/类路径、内存建议、输出路径、预计成本及所属历史版本。由现有 `planning-benchmark.gradle` 获取类路径，提供统一脚本负责编译选定工具到独立 build 子目录并运行，不把审计程序混入生产 JAR。

验收：25 个入口都有记录；先检查硬编码本机路径与缺失资产，缺失依赖明确标记。对可用程序使用最小参数逐个做启动/输出冒烟验证，昂贵全尺寸审计另记运行证据；不能仅凭类路径任务通过就宣称工具可复现。

### 11．`CoastGenerator.Result` 的重复采样和空 `phases`

依据：[CoastGenerator](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/terrain/CoastGenerator.java)、[CostPlanner](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/cost/CostPlanner.java)。

方案：默认删除未消费的 `equalArcSamples` 与空 `phases` 字段及其生成计算，保留 `CostPlanner` 按注入 profile 在需要时采样。这样避免在生成海岸和恢复海岸间增加不同的数据通路。将空数组相等断言替换为同种子海岸顶点、几何约束和等弧采样结果的有效断言。

验收：海岸顶点、实际成本参考采样顺序和等级海岸参考值不变，生成阶段不再重复分配采样列表。删除 record 组件前检查调用和公开兼容范围。

### 12．`MountainTerrain` 未进入生产装配

方案：先将其回归测试的有效覆盖迁到生产路径 `TerrainRecipes`、`MountainRangePlan`、`RegionTerrain`/`IslandMacroTerrain`；随后删除死类。若其确为有价值的历史算法对照，移至测试参考实现并明确用途，不继续把它作为生产能力。

验收：生产山地高度、山脉连续性和典型种子回归仍有断言；主代码无该类引用，不能因删除类连同有价值的山地验证一起丢失。

### 13．`occupied`、无调用重载与 `VanillaAltitudeSnow`

依据：[JointPlanner](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/planner/JointPlanner.java)、[VanillaAltitudeSnow](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/planner/VanillaAltitudeSnow.java)。

方案：删除从未读取的占用集合、传参和无调用重载，保留 `spacingAllows`、物理占地/地块保护重叠检查。不要把原本传 `Set.of()` 的位置改为传真实集合，这会额外启用此前未生效的筛选规则。`VanillaAltitudeSnow` 按第 12 项方式移至测试参考或删除；生产雪/表层效果继续由已采用的原版流程负责。

验收：同 ID 结构最小/最大间距、不同实例占地冲突和保护范围仍通过；固定种子的结构入口、数量和归属不变。测试参考不得反向成为生产依赖。

### 14．内部硬引用 `PlannerProfile.V2` 与散落预算

方案：仅在生产装配入口选定 `PlannerProfile.V2`，向 PlacementIndex、BiomeAllocationPlanner、JointPlanner、TerrainCapacitySolver、FillerLayout 传入当前 profile 或相应只读预算。把 `BUDGET=12_000_000` 提升为具有明确计数单位的竞争增长预算，默认值不变，不随意复用含义不同的已有字段。

联动检查 `CostPlanner.Result.refine` 中的 V2/版本字符串以及运行时恢复工厂，保证首次规划与恢复采用同一参数来源。`PlanV2Codec` 对已确定 plan-v2 协议的检查可以固定，不应把所有 V2 引用机械替换成可变参数。新可变参数若影响输出，必须被算法身份或规范有效参数摘要区分。

验收：注入一个更小预算和不同版本标记的测试 profile，各子阶段确实使用它，失败位置与预算一致；默认 V2 的布局、预算操作计数和随机输出保持不变。新增参数不得形成未纳入身份的隐式算法分支。

### 15．等级硬约束关闭、软偏好使用粗网格

方案：保留当前产品语义。生产 `LevelConstraint.accepts=true` 改为语义明确的软偏好接口/命名，或显式标注这是兼容旧接口的无硬筛选策略；把 `CostPlanner.Result.accepts`、`AdventureLevels.contains` 标为历史/诊断用途，核实外部调用后迁移或删除。成本说明明确生产偏好取粗网格节点成本，细化成本不作为等级硬准入。

验收：等级仍能影响候选排序，但不以等级区间拒绝其他条件合法的位置；出生安全、结构承载及环境硬约束仍成立。若未来要让偏好改吃细化成本，单列行为与性能变更，不能混在此次命名清理中。

### 16．成本预算守卫异常类型不统一

方案：将节点数和预估内存超限都归为 `PlanningFailure(RESOURCE_LIMIT)`，统一阶段为 `cost-graph`，附 actual/limit 与单位。把可预估的检查提前到大数组分配和整图采样之前；尺寸乘法使用检查溢出的 long 运算。非法 API 参数仍属于参数错误，不用一个泛化 catch 将所有 `IllegalArgumentException` 转为资源不足。

验收：分别以极小节点上限、极小内存上限触发明确失败；边界等于上限合法；可导致尺寸溢出的输入在分配前受控失败；原成功用例结果一致。

### 17．细化结果缓存缺少显式容量约束

方案：先统计生产调用和对象生命周期。当前软偏好不调用 `refinedCostAt`，所以两个结果 map 的风险是细化 API 被持续查询后的保留量；局部 `GridCostGraph` 会随一次 refine 结束释放，本身不是长期持有全世界的图。

为 `refinements` 设置按 tile/字节计费的容量，为 `exactCosts` 设置条目上限，并隐藏可变 map 的公开写入口。由同一工作内存预算分配额度，计入进行中的并发细化；值计算完成后发布，淘汰只导致重算，不能改变成本或搜索终止语义。局部图优先保持实现，只有测量表明值得时才替换为等价的紧凑数组图；复用为长期图时必须明确边界。

验收：大量不重复坐标查询后保留量受限；冷/热/淘汰后以及正序/逆序/并发查询得到相同精确成本；覆盖负坐标与 tile 边界。操作预算不得以缓存命中率或并发调度决定规划是否成功，性能另测重算开销。

### 18．边缓存统计名称含糊

方案：先纠正原文：`computations` 是已计算的规范化无向对数，阻断边也计入；它不是“有向对数”，也不是预分配槽位数。在统计和日志中分别命名 `computedPairs`、`allocatedSlots`、`hits`；如需理论有效相邻对数，另行计算并明确不包含越界槽位。无需改变边算法。

验收：小网格上一次正向查询后反向查询不增加计算对数，阻断结果可复用；已分配槽位等于实现的 `nodeCount*4`，不被当作实际边数。现有持久化 `cost_edges` 先保持线字段及原数值含义，若改名须单列协议调整。

### 19．水文档案包含未生效参数

方案：区分移植参考向量与实际运行参数。把未使用的湖起点距离、湖岸高度四项标为参考字段并迁入参考模型，运行 profile 只公开有效项。平滑的 `iterations/radius/rate` 与 ErodedTerrain 实际使用的单次、1.8 方块、0.9 统一到一个有效参数来源；首轮只支持当前语义，拒绝未实现的非默认值，而非悄悄忽略。

不要直接将湖参数接入选点或把多次平滑解释为当前单次滤波，这会改变输出。扩大参数范围时再定义采样半径、边界、迭代快照、坐标单位和冻结恢复方式。

验收：默认河湖/侵蚀/平滑黄金采样不变；有效参数有消费方和有效性验证，参考字段不再宣称可调运行效果。若后续支持改变参数，改变它们必须产生可解释输出变化并进入身份/冻结数据。

### 20．水文 v1/v2 文档混用

验收：当前文档无未解释的 v1 声明；历史 v1 每处能找到适用日期/版本。禁止全仓替换 `v1`，尤其不能误改 `FTF_ADAPTED_V1` 参考向量名或让旧报告声称验证过 v2。

验收：完整哈希可从源码直接复制，所有来源记录一致，许可证声明保留；本项不改算法或计划身份。

### 22．气候诊断自行按固定阈值分带

依据：[ClimateDiagnostics](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/planner/ClimateDiagnostics.java)、[ClimateField](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/climate/ClimateField.java)。

方案：`distribute` 直接使用 `field.band(...)` 与温度类型 ordinal 比较，和 actual/supply 统一。`ClimatePlan.value(...)` 当前返回 base，而非 `valueAt` 的标准化值，不能以固定 2.5/5/7.5 重建任意冻结场的分带；契约和诊断测试一起调整。

验收：合成场使用非默认阈值，并构造 base 值和最终 band 不一致的场，target/actual/supply 都遵从 band；默认有机温度场的统计保持预期。该统计虽不反馈布局，却会持久化，因此统计变化需单独核对规范字节，不能称为绝对字节不变。

### 23．湿度供给缓存的实际准入范围

依据：[HumiditySupplyCorrection](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/climate/HumiditySupplyCorrection.java) 的 `correct` 与 [TerrainRule.accepts](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/config/AdventureWorldConfig.java)。

方案：撤回“同键跨高程导致掩码错误”的现状结论。代码已排除有 minHeight/maxHeight 的规则；其余准入依赖地形类别、主配方、有无有效次配方及地貌，均被当前键覆盖。保留现行算法，补充注释：供给只统计无高度限制、非 shore-only 的填充规则，属于模板/地貌层面的供给修正，并不保证该位置所有最终准入条件成立；mask=0 时原值保留。

验收：同键不同高度、交换查询顺序时结果一致；带高度限制/shore-only 规则不影响掩码；无供给时返回原值。未来若决定把高度规则纳入修正，必须按高度阈值区间扩键或逐点重算，并另列行为变更，不能仅删除排除条件。

### 24．四分格温度缓存与样本一致性缺少守卫

方案：让冻结场公共查询在内部按四分格中心量化坐标，并从同一冻结地形获取对应 MacroSample，使缓存值成为坐标和冻结状态的纯函数；内部热路径可保留接收“已量化样本”的入口，但限制可见性并明确契约。不要把浮点 sample 对象整体追加到缓存键，也不要让首次传入的任意样本决定整格结果。

验收：同格不同坐标/高度参数和不同首次调用次序返回约定的中心值；负坐标使用 floor 量化，覆盖格边界；首次规划与 READY 查询一致。生产当前合法中心调用的输出须保持，测量重新获取样本带来的开销；若现有公共 API 允许非中心精确采样，保留独立的无缓存精确入口并明确语义。

### 25．失败阶段与进度阶段命名空间不同

方案：保留二者不同粒度，集中失败阶段为有稳定字符串值的标识类型，继续输出原 `stage` 字符串；建立到 `PlanningStage` 的显式多对一映射供 UI/日志使用。失败码、失败阶段、用户可读说明分别承载机器分类、定位与文案，不再让自动化从自由说明中猜测阶段。

验收：每个生产失败阶段都能映射到进度阶段或明确“不适用”；原诊断字符串保持兼容，新增阶段需登记；资源不足和搜索预算耗尽仍可分别匹配。外部读取未知 stage 时有明确回退，不能依赖 enum ordinal。
