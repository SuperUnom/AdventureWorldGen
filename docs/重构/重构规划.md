# AdventureWorldGen 重构规划

[返回项目总览](../../README.md) · [当前配置说明](../配置说明.md) · [运行时与结构适配](../运行时与结构适配.md)

日期：2026-09-10  
状态：规划草案；本文记录拟实施的结构调整，不表示代码已完成重构，也不自动修改现有生成规则。  
依据：本轮对当前源码、测试源码和文档的静态检查；本轮未重新运行构建或游戏测试。

## 1．目标与实施边界

本次重构的目标是明确环境生成、群系与结构规划、计划数据、Minecraft 执行和内容兼容之间的职责，使后续修改集中在对应模块，并能独立验证。

优先解决三个问题：

1. 地形、水文、温湿度场与群系决策相互混合，难以判断一次配置或算法修改会影响哪些结果。
2. 专用结构适配器已经存在，但通用区块生成器仍写死沙漠神殿部件，扩展契约没有贯通。
3. 计划数据、首次构建、存档恢复和运行时查询耦合，当前文档又混有多轮旧规则，增加维护成本。

实施原则：

- 保留单个 Gradle 工程，按职责逐步调整包和类，不提前建立多个构建模块。
- 保留 Planner 决定宏观布局、Noise 提供局部变化的分工。
- 第一轮结构调整保留当前算法、随机键、遍历顺序、数值、失败与回退行为；改变这些内容须单列为行为变更。
- 不因类较长就拆分；优先拆分会独立变化、需要不同依赖或可以独立验证的职责。
- 每阶段形成可编译、可验证的完整结果，不同时迁移所有包。
- 本规划不承担重选温湿度算法、改变最低面积回退、增加精细路线验证等产品设计任务。

## 2．当前问题与源码依据

| 问题 | 当前证据 | 对后续开发的影响 |

| 气候与群系规则混合 | [ClimatePlan](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/climate/ClimatePlan.java)包含温度场、湿度组织、准入、评分、海岸群系规则、需求统计和旧状态恢复 | 环境场与“某群系能否放这里”没有独立边界 |
| 湿度被填充配置反向修正 | [HumidityPlan](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/climate/HumidityPlan.java)在 `computeValue` 中按填充群系的可用湿度类型修正湿度值 | 更换填充池可能改变环境场，依赖不够直观 |
| 水文包含方块选材 | `hydrology.RiverSediments` 直接输出原版方块调色板（该实现已随 P5.2 删除，材料交还原版地表流程） | 替换河床材料需要进入水文包 |
| 结构扩展没有贯通 | [AdventureChunkGenerator](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/worldgen/AdventureChunkGenerator.java)恢复冻结部件时只接受 `minecraft:tedp`，直接构造 `DesertPyramidPiece` | 新增结构适配器仍可能要求修改核心生成器 |
| 接口与生产执行不一致 | [StructureAdapter](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/api/StructureAdapter.java)声明 `serializePieces`、`placeChunk`，本轮未发现生产路径调用；测试中存在 `placeChunk` 调用 | 接口看似支持完整接入，实际落地走另一条路径 |
| 内容规则散落 | `GeneratedAdventurePlan.inlandWaterBiome`硬编码原版寒冷群系；[MinecraftAdapters](../../neoforge/src/main/java/io/github/luoyan/adventureworldgen/worldgen/MinecraftAdapters.java)混合注册、默认材料和专用实现 | 模组内容扩展容易演变成向核心追加 ID 分支 |

现有基础可以保留：`terrain`、`hydrology`、`erosion`、`cost` 已有领域划分；`AdapterRegistry` 已具备注册和冻结机制；JUnit 与隔离测试伴生模组已存在。上述判断不等同于这些测试已在当前环境重新通过。

## 3．目标职责与依赖

以下是目标职责表。包名为建议名称，实施时可以在保留公开入口的前提下调整；仅在迁移实际代码时建立目录。

| 包或模块 | 负责 | 边界 |
|---|---|---|
| `api` | 第三方适配契约、只读查询接口及注册入口 | 不容纳内置原版实现；不依赖具体运行时实现 |
| `config` | 作者配置模型、解析、语义校验 | Minecraft 数据包读取与注册表查询由接入层提供 |
| `plan` | 地块、结构、冻结环境状态、计划快照、版本信息等共享数据 | 不在构造函数内执行规划，不承担查询缓存或游戏生命周期 |
| `planner` | 阶段编排、地形容量预留、群系与结构求解、约束检查及回退 | 通过接口使用环境查询、结构准备和进度通知 |
| `terrain` | 海岸、区域地形、山脉、海底、高度采样及地形组合 | 消费已确定的容量/区域结果，不自行处理群系配额 |
| `hydrology`、`erosion` | 河湖几何、水位、河床形态、侵蚀场及其地形作用 | 不直接选择 Minecraft 方块或群系 ID |
| `climate` | 温度场、湿度场、分带与环境查询；显式的场修正策略 | 不承担群系播种、面积竞争和内容 ID 特例 |
| `biome` | 环境准入与偏好评分、群系归属查询、过渡和水体群系选择策略 | 从环境场读取数据；面积分配流程由规划器驱动 |
| `surface` | 地表与河床材料选择策略 | 水文形态与具体材料可以分别调整；Minecraft 方块操作仍在接入层 |
| `runtime` | 计划查询服务、会话生命周期及查询缓存的组装 | 不重新决定宏观布局，不包含专用结构类型分支 |
| `persistence` | 冻结数据编解码、完整性检查、原子保存与加载 | 返回计划数据；不在解码过程中隐式重新规划 |
| `worldgen` | Minecraft 区块流程、注册表桥接、通用结构恢复和起点注入 | 面向通用契约执行；不直接引用沙漠神殿等专用实现 |
| `compat.vanilla` | 原版内容的专用适配、默认规则与必要兼容实现 | 向公共注册入口提供实现，不反向修改核心算法 |
| `noise`、`spatial` | 公共噪声、坐标、网格及确实共用的基础工具 | 不依赖规划或运行时；不要成为杂项收纳包 |

气候相关数据流应当显式可见：

```text
冻结地形与水文 → 温度场 → 自然湿度场 → 湿度供给修正策略 → 环境查询
                                                        ↓
作者群系规则 ───────────────────────────────────→ 准入与评分
                                                        ↓
                                               群系与结构规划
```

这是依赖说明，不要求重新排列当前生成阶段。地形容量预留仍然可以读取作者需求，但由规划阶段显式执行；湿度供给修正仍可读取填充规则，但依赖必须从接口和数据流中体现。温度、湿度之间正常的单向依赖无需消除。

跨层共享数据放入 `plan` 或对应领域的只读数据类型。仅仅使用 record 不代表不可变：数组、列表、蒙版和 NBT 字节需要保持防御性复制或明确的只读所有权。

## 4．重点拆分方案

### 4.1 环境场与群系决策

- 从 `ClimatePlan` 提取温度计算和冻结状态，保留当前自然温度参数与旧状态识别逻辑。
- 将湿度计算、海岸距离查询、湿度供给修正、群系湿度准入分开；第一轮不删除当前供给修正。
- 将温湿度允许范围、权重评分、硬高度及海岸群系优先规则集中到群系环境规则服务，供播种、扩张、填充和过渡共用。
- 将供需统计、目标比例和日志整理为独立诊断结果，避免统计对象参与不明确的环境修正。
- 将 `LocalBiomeBlend` 等群系过渡逻辑移至群系职责范围；公共噪声从地形包提取。
- 将 `TerrainCapacityPlan` 中的求解过程与只读预留结果分开，使地形采样器仅消费结果。

旧算法恢复逻辑可以保留在明确的版本实现中；在确认现有存档策略之前，不直接删除旧状态字段或改变解码选择。

### 4.2 计划数据、构建与查询

拟形成三个明确入口：

1. **首次规划**：显式执行环境、布局、填充、过渡保护和终检，得到完整快照。
2. **READY 恢复**：解码冻结数据、检查格式和输入身份，通过统一工厂恢复查询对象；不得重新分配群系或改变结构随机选择。
3. **运行时查询**：读取快照与领域采样器，仅使用不改变生成结果的缓存。

`GeneratedAdventurePlan` 可先作为兼容门面保留，逐步将构建工作移出。统一地形组装工厂应保留首次规划时复用已计算对象的优化，避免为结构整洁而增加重复采样与内存副本。

从算法中移除对静态 `PlanningProgress` 的直接调用，改为阶段回调或小型观察接口。计时、日志和界面更新由外层承接；算法预算继续使用既定操作计数，不能改成墙钟终止。

`PlanV2Codec` 和配置解析器后续可按领域提取子编解码器，但先建立稳定的数据边界，避免为了拆文件创建大量相互转发的类。

### 4.3 结构适配完整路径

目标路径：

```text
内容预检 → 专用/通用适配器准备结构 → 冻结部件与入口、占地
        → 统一计划保存 → 按注册类型恢复部件 → 统一注入结构起点
```

具体任务：

- 将 `VanillaDesertPyramidAdapter` 移入原版兼容包；入口、旋转和特殊占地验证保留在专用实现。
- 提取公共部件序列化与恢复设施。实施前核对当前 Minecraft 版本的部件注册和加载上下文，优先复用注册机制；不能假定任意 NBT 都能无上下文恢复。
- 删除通用区块生成器中的 `minecraft:tedp` 判断和 `DesertPyramidPiece` 构造；不以更长的结构 ID 分支替代。
- 以当前冻结部件、恢复并注入 `StructureStart` 的生产路径作为统一方向。对无生产调用的 `serializePieces`、`placeChunk` 明确迁移或废弃安排，避免同时承诺两套不一致的执行机制。
- 预检区分“已注册结构 ID”“能冻结全部随机选择”“能恢复部件类型”这些能力；不支持的受控结构尽早给出内容 ID 和失败原因。
- 保留通用结构原生候选抑制、跨区块引用、旋转、入口和随机选择冻结等约束。

通用部件恢复不等于所有结构自动支持规划。复杂拼图、特殊生成上下文或专用入口仍可能需要适配器；新增适配器应通过公开扩展点完成，而无需修改核心生成器。

### 4.4 内容规则与兼容实现

| 类型 | 处理方法 | 首批对象 |
|---|---|---|
| 只有 ID、材料或数值不同 | 默认规则集中管理，随后按需要提供数据包覆盖 | 内陆水体群系映射、河床材料、默认群系适配数据 |
| 真正特殊的内容行为 | 保留小型专用适配器，放入兼容包 | 沙漠神殿准备、入口与占地验证 |
| 可以依据通用能力处理 | 继续使用属性/能力判断，放在公共 Minecraft 桥接处 | `StructureTerrain` 的地基适配 |
| 旧接口或仅测试使用的实现 | 核对调用与公开承诺后废弃、迁移或转为测试参考 | `VanillaAltitudeSnow`、`allowsSnowClass`、旧地表调色板接口 |

数据规则首轮以复制当前默认效果为目标。若加入显式映射与标签，需定义优先级、未知 ID、多个来源冲突及缺省行为；建议显式 ID 映射高于标签默认，冲突不依赖加载顺序悄悄覆盖。

对任意新模组寒冷群系自动选择冻结河流属于新增能力，需要另行明确依据。第一轮不能简单把当前 ID 列表替换成另一套温度判断并视为行为不变。

## 5．分阶段实施

| 阶段 | 工作与交付 | 进入下一阶段的条件 |
|---|---|---|
| P0：规则与基线 | 整理当前规则索引及冲突表；核对已有测试；记录固定种子、配置、版本、输出和性能基线；为旧 READY 样本记录来源 | 当前行为与期望规则可区分；确定性、恢复和游戏验证入口可复现 |
| P1：共享数据与基础依赖 | 提取计划数据；算法改为进度接口；迁移公共噪声和缓存工具；隔离数据包加载与 Minecraft 注册表依赖 | 算法不依赖具体运行时数据类或静态界面进度；输出基线一致 |
| P2：环境与群系边界 | 拆出温度、湿度、修正策略、准入评分和诊断；分开容量求解与结果；整理群系过渡和地表职责 | 各阶段使用同一套准入规则；默认温湿度、归属和地形结果保持一致 |
| P3：构建与恢复边界 | 显式计划构建、快照终检和查询工厂；缩小 `GeneratedAdventurePlan`；存储层只处理冻结数据 | 首次构建与 READY 重载查询一致；恢复不重复执行布局求解；性能无未解释退化 |
| P4：结构适配贯通 | 通用部件恢复与起点注入；迁移原版专用适配；清理未接通接口；补真实异类部件测试 | 非沙漠神殿部件能通过扩展点完成准备、保存、重载和生成；核心无专用部件分支 |
| P5：规则扩展与收尾 | 集中水体群系、材料默认规则；按已确定范围增加数据覆盖；整理旧接口、版本恢复代码与文档归档 | 默认效果可对照；新扩展行为有单独验证；文档与实际接口一致 |

默认依次推进。若近期首要任务是接入新结构，P4 可在 P1 的共享数据和接口边界稳定后提前执行，避免等待全部气候整理。每次只完成一个可审查的迁移单元，不同时搬迁全部领域。

第一批建议范围为 P0 与 P1。完成后按新功能方向选择先做 P2，还是提前贯通结构适配。

## 6．验证与兼容约定

### 6.1 输出与性能

- 优先复用已有确定性、地形固定输出、温湿度、群系面积、结构、缓存、持久化和 GameTest；只补充能发现边界错误的缺失测试。
- 固定种子、相同配置和算法身份，对照地形/水位采样、温湿度分带、群系归属、出生位置、结构入口与部件 NBT。
- 在序列化协议不变时对照计划规范字节或哈希；不能靠更新期望值掩盖重构引入的输出差异。
- 覆盖负坐标、边界位置、不同查询顺序，以及首次构建与 READY 重载的一致性。
- 同机同配置对照首次规划、重载、区块查询与峰值内存。先测量波动范围；出现超出波动的持续退化时定位原因，不能仅以功能测试通过结项。
- 涉及 Minecraft 桥接、结构恢复或地表行为时，追加对应真实 GameTest/服务器验证；纯文档调整只做链接和内容检查。

### 6.2 结构扩展专项验收

现有测试驿站内部复用了 `DesertPyramidPiece`，不能证明任意部件类型的恢复能力。P4 必须加入至少一种不同部件类型，并覆盖：

1. 从适配注册入口完成接入，核心生成器没有为它增加分支。
2. 准备结果经保存、READY 重载后保持部件、旋转、入口与占地一致。
3. 跨区块起点和引用正确，受控结构原生候选仍被抑制。
4. 重复处理不产生额外结构，战利品或方块实体数据正确保存。
5. 不支持的恢复类型在尽可能早的阶段产生明确诊断。

### 6.3 存档与公开接口

- Java 包调整与存档格式调整分别评估。不得因为改了类名就默认可以更改存储字段或使 READY 无条件失效。
- `plan-v2` 中使用 Gson 直接序列化的布局状态需特别检查字段、默认值和嵌套结构，提取数据类时保留现有线格式。
- 核对算法身份、实现修订、适配器版本和输入哈希之间的关系，集中维护版本信息。
- 对规则资源增加覆盖能力后，实际影响输出的规则必须进入输入身份计算；运行时使用本次计划冻结的有效规则或可验证的同版本规则，避免重载资源后悄悄改变旧计划查询。
- 本轮不扩展长期存档迁移承诺。若某阶段确需协议升级或公开接口破坏性调整，先形成具体影响清单、过渡方式及测试方案，单独审查。

## 7．文档整理安排

- 专题文档完整说明当前规则，减少“正文旧算法＋页首多轮覆盖说明”的阅读方式。
- 历次 r6～r33 实现记录、实验方案和旧算法保留为历史资料，并标明各自版本与证据范围。
- 可逐步归入“历史版本”“变更记录”“实验”“参考资料”；本轮不先移动所有文件，避免产生大规模断链。
- README 保留项目定位、当前状态和开发入口，更新记录通过索引进入。
- 将本规划的目标依赖和实际迁移结果逐步落入开发说明；未完成阶段继续标为计划。
- 文档冲突按对应变更记录、用户已确认决定和当前代码共同核对，不能仅以代码现状或最新文件时间自动决定产品语义。

## 8．需要单独决策的事项

以下事项不阻塞保留行为的结构整理，但不能在重构时隐式决定：

| 事项 | 本规划的默认处理 | 何时单独决策 |
|---|---|---|
| 湿度是否继续受填充池影响 | 保留并提取为显式策略 | 希望更换填充配置也不改变自然湿度时 |
| 模组寒冷群系如何匹配水体群系 | 保留当前默认映射，集中规则 | 增加标签、气候推断或自定义水体群系时 |
| 数据规则覆盖范围 | 先集中默认值与加载边界 | 真正新增作者字段、标签或资源格式前 |
| 旧算法状态与公开适配接口保留多久 | 先盘点调用与存档样本，不直接删除 | 提出具体删除、格式升级或破坏性修改时 |

## 9．完成标准

- 修改温度计算主要涉及气候模块，不需要同时修改结构或区块执行代码。
- 群系准入在播种、增长、填充、过渡中使用一致规则，环境修正策略可定位、可独立验证。
- 地形和水文核心不包含具体方块选材，也不根据专用结构 ID 分支执行。
- 新增符合支持能力的结构通过注册扩展完成，无需修改通用区块生成器。
- 计划数据、首次构建、存档恢复和查询缓存具有明确边界，确定性与重载一致性有当前证据。
- 当前规则、扩展接口和历史验证记录可分别找到；规划状态与已完成实现不会混写。

这些条件全部有对应代码、文档和验证证据后，才将重构标记完成。
