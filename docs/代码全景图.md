# 代码全景图

[返回项目总览](../README.md) · [文档索引](README.md) · [运行时与结构适配](运行时与结构适配.md) · [配置说明](配置说明.md)

本文回答一个具体问题：**这个模组的每个包各自负责什么，一次世界生成从入口到区块方块经过哪些对象、按什么顺序被调用。**

它不替代任何现行契约。[设计原则](设计原则.md)定义产品语义，[配置说明](配置说明.md)定义作者字段，各算法文档定义求解步骤，[运行时与结构适配](运行时与结构适配.md)定义落地与持久化。本文只做一件事：把**代码里真实存在的调用链条**画出来，并给每条边一个 `文件:行` 的出处，便于改动前定位影响面。

阅读约定：

- 行号对应 2026-09-11 的 `codex/重构` 提交 `2e44136`；改动代码后行号会漂移，符号名和调用方向仍有效。
- “未被调用”“未被验证”这类判断只在有证据时写出；无法确认的地方写“未能确认”，不按印象补全。
- 调用边一律标注方向。依赖边来自实际 import（含内联全限定名），不是设计意图。

## 1．工程与代码规模

单个 Gradle 工程，三个 source set，全部代码在一个 mod 内，没有提前拆分多模块。

| 位置 | 内容 | 规模 |
|---|---|---|
| `neoforge/src/main/java/.../adventureworldgen/` | 生产代码，18 个包 | 130 个文件 |
| `neoforge/src/test/java/.../` | JUnit 单元与结构测试 | 58 个文件 / 191 个 `@Test` |
| `neoforge/src/testmod/java/.../testcompanion/` | 隔离的测试伴生模组 | 12 个文件 / 24 个 `@GameTest` |
| `neoforge/tools/` | 一次性审计/预览程序与 Gradle init 脚本 | 36 个文件（25 个带 `main()` 的程序 + 7 个 `.gradle` + 4 个 Python 脚本），**不属于任何 source set** |

构建契约在 `neoforge/gradle.properties`：Minecraft 1.21.1、NeoForge 21.1.249、Java 21、mod id `adventureworldgen`。
运行入口在 `neoforge/build.gradle`：`client`、`server`、`gameTestServer`（带 testcompanion）、`testCompanionServer`、`planningSmokeClient`。

## 2．分层与依赖全景

### 2.1 实测依赖图

箭头 `A → B` 表示 `A` 的源码里出现 `B` 包的全限定引用（import 或内联）。这是实测结果，不是设计意图。

```text
worldgen     → api, compat, config, persistence, plan, runtime
runtime      → api, biome, climate, compat, config, cost, erosion, hydrology,
               noise, persistence, plan, planner, spatial, terrain
planner      → api, biome, climate, config, noise, plan, spatial, terrain
persistence  → api, erosion, hydrology, plan, spatial, terrain
hydrology    → api, noise, plan, spatial, terrain
erosion      → api, hydrology, noise, plan
cost         → api, plan, spatial, terrain
compat       → api, plan
biome        → api, climate, config, noise, plan
climate      → api, config, noise, plan
config       → api, plan, terrain
terrain      → api, noise, plan, spatial
api          → plan
plan         → spatial
noise        → spatial
spatial      → （无内部依赖）
mixin        → worldgen
client       → runtime
```

**逐句对照**（每行读作"左边的包引用了右边这些包"）

- `worldgen → api, compat, config, persistence, plan, runtime`　游戏执行层把契约（`api`）、内置原版适配器（`compat`）、作者模型（`config`）、冻结数据（`persistence`、`plan`）和会话查询（`runtime`）都接了起来——它是唯一同时看到"契约"和"游戏"的包。
- `runtime → api, biome, climate, compat, config, cost, erosion, hydrology, noise, persistence, plan, planner, spatial, terrain`　会话与组装层指向**几乎所有**领域包：`RuntimePlanner` 需要按顺序把它们串起来。这是全项目最宽的一行，也是它作为"汇合点"的证据。
- `planner → api, biome, climate, config, noise, plan, spatial, terrain`　联合求解要读群系准入（`biome`）、温度湿度场（`climate`）、作者需求（`config`）、地形（`terrain`），但不依赖 `runtime`、`cost`、`hydrology`、`erosion`、`persistence`。
- `persistence → api, erosion, hydrology, plan, spatial, terrain`　存储层要能原样编解码海岸、河网与侵蚀场，所以引用这些领域结果；**不引用 `runtime`**。
- `hydrology → api, noise, plan, spatial, terrain`　河网生成读地形与海岸，用噪声做抖动，输出冻结计划数据。
- `erosion → api, hydrology, noise, plan`　侵蚀用 `hydrology` 里的参数集（`HydrologyProfile` 同时承载两者），并在 `api` 的地形契约上工作。
- `cost → api, plan, spatial, terrain`　代价图读地形与海岸线，用 `spatial` 的向量与缓存。
- `compat → api, plan`　原版兼容实现只用契约与词汇层——这就是"兼容层不得反向改核心"在依赖图上的样子。
- `biome → api, climate, config, noise, plan`　准入规则读气候场与作者偏好，用噪声做域扭曲；**不引用 `planner`**（`planner` 反过来调用它）。
- `climate → api, config, noise, plan`　两个场需要作者参数（半径、偏好）与噪声，但**不引用 `planner`**——需求统计是注入进来实现的。
- `config → api, plan, terrain`　作者模型认识地形的词汇（配方枚举、地形设置）与地形策略接口。
- `terrain → api, noise, plan, spatial`　地形只依赖契约、噪声、词汇层与基础件；**不引用 `config`**（作者信息以单方法策略注入）、**不引用 `planner`**（容量预留以冻结结果消费）。
- `api → plan`　契约层只认识内容 id 与失败类型。
- `plan → spatial`　冻结状态里存所有权网格，所以需要 `spatial` 的格坐标。
- `noise → spatial`　域扭曲返回二维向量。
- `spatial →（无内部依赖）`　**唯一空的一行**，这是它必须保持的性质：`plan` 依赖它，它一旦反向依赖回来就成环。
- `mixin → worldgen`　唯一那个 mixin 把决策委托给 `worldgen.MountainSpringFilter`，自己不写规则。
- `client → runtime`　加载界面只读 `PlanningProgress` 的快照；**不引用 `worldgen`**，所以画界面不需要懂生成。

值得单独记下的几条：

- **`spatial` 是唯一没有内部依赖的包**：`plan` 依赖它的所有权网格，所以它一旦反向依赖回来就是环。
- **`runtime` 是唯一的汇合点**：14 个包指向它，它指向 15 个包。所有“横切”的组装都发生在这里。
- **只有 4 个包接触 Minecraft**：`worldgen`（12 个文件里 8 个）、`compat`（2 个里 1 个）、`client`（1 个）、`mixin`（1 个）。其余 14 个包是纯算法与数据，可在单元测试里脱离游戏运行。
- **`surface` 包目前不存在**：`PackageBoundaryTest` 里有针对它的规则，但源码树没有该目录，测试用 `assumeTrue` 跳过。地表材料现在由原版表面规则承担（见 6.4）。

**怎么读这张图**：每一行是 `<包> → <它引用的包>`，也就是"改这个包时，可能被它影响的下游有哪些"。箭头方向是**依赖方向**（左依赖右）。越靠下的包被越多包依赖，越不该频繁改动：`spatial` 在最底部，`plan` 次之，而 `runtime` 与 `worldgen` 站在最上面，是把算法接到游戏上的那一层。这张表是**实测结果**（扫描源码里的全限定引用），不是设计意图——所以它同时也是"注释说的和代码做的是否一致"的检查工具。

`src/test/java/.../PackageBoundaryTest.java` 不是行为测试，而是**源码级依赖测试**：它扫描整个文件（含内联全限定名，剥离注释后），禁止某些包引用某些前缀。这是理解分层最快的入口，规则逐条列出：

| 测试方法 | 锁定的事实 |
|---|---|
| `configLayerHasNoMinecraftOrNeoForgeDependency` | `config` 不碰 `net.minecraft` / `net.neoforged`；数据包读取与注册表查询由 `worldgen.ProfileReloadListener` 提供 |
| `planningAlgorithmsDoNotDependOnTheRuntimeLayer` | `planner` 不引用 `runtime`（进度改为显式观察者参数） |

| `sharedBasePackagesDependOnlyOnEachOther` | `noise` 只能用 `spatial`；`spatial` 不能引用本模组任何其他包 |
| `adapterAndConfigLayersDoNotDependOnPlanning` | `api` 不含内置实现；`config` 不触达求解器与会话 |
| `surfaceMaterialsDoNotDependOnHydrologyOrExecution` | `surface` 的规则（当前无源码，跳过） |
| `terrainConsumesReservedResultsWithoutDoingDemandSolving` | `terrain` 不引用 `planner` / `runtime`，只消费冻结的容量结果 |
| `biomeStrategiesDoNotDependOnPlanningOrGameLifecycle` | `biome` 不引用 `planner` / `runtime` |
| `vanillaCompatibilityCarriesNoCoreDependency` | `compat` 只用 `api` 与 `plan` |

## 3．主调用链条（按发生顺序）

这一节是本文的主干。每一步给出触发者、被调用的类与方法、以及产物。

### 3.1 模组加载：注册两个 worldgen 对象

```text
NeoForge 构造入口
 └─ AdventureWorldGen.<init>(IEventBus)                    AdventureWorldGen.java:10
     └─ ModWorldgen.register(bus)                            worldgen/ModWorldgen.java:28
         ├─ CHUNK_GENERATORS.register("adventure")           worldgen/ModWorldgen.java:19
         └─ BIOME_SOURCES.register("adventure")              worldgen/ModWorldgen.java:23
```

**逐句对照**

- `NeoForge 构造入口`　NeoForge 用构造器注入的方式实例化模组主类，并把模组事件总线递进来。
- `└─ AdventureWorldGen.<init>(IEventBus)`　主类构造器只做一件事：把总线转交给注册入口。
- `└─ ModWorldgen.register(bus)`　注册入口把两个 `DeferredRegister` 挂到总线上。
- `├─ CHUNK_GENERATORS.register("adventure")`　登记区块生成器的编解码器，id 为 `adventureworldgen:adventure`。
- `└─ BIOME_SOURCES.register("adventure")`　登记群系源的编解码器，用同一个 id。

两个 `DeferredRegister` 把 `AdventureChunkGenerator.CODEC` 与 `AdventureBiomeSource.CODEC` 登记为 `adventureworldgen:adventure`。
普通主世界自动启用不靠代码分支，而靠数据包覆盖：`src/main/resources/data/minecraft/worldgen/world_preset/normal.json` 把主世界生成器替换为

```json
{ "type": "adventureworldgen:adventure", "profile": "adventureworldgen:default" }
```

因此**生成器的序列化形态里只有一个 profile id**（`AdventureChunkGenerator.java:53`），其余全部状态在运行时由计划提供。

### 3.2 资源重载：作者配置变成不可变 `LoadedProfile`

```text
AddReloadListenerEvent
 └─ AdventureEvents.addReloadListeners                     AdventureEvents.java:36
     └─ new ProfileReloadListener()                        worldgen/ProfileReloadListener.java
         ├─ prepare(ResourceManager, ProfilerFiller)       ProfileReloadListener.java:35
         │   ├─ resources.getResourceStack(default.json)    ProfileReloadListener.java:36
         │   ├─ 检查栈深度 ≤ 2（内置 + 至多一个数据包）        ProfileReloadListener.java:40
         │   ├─ AdventureWorldConfigParser.parse(reader)    config/AdventureWorldConfigParser.java
         │   ├─ CanonicalConfigJson.write(config)           config/CanonicalConfigJson.java
         │   └─ AtomicPlanRepository.sha256(canonical)      persistence/AtomicPlanRepository.java:98
         └─ apply(LoadedProfile, ...) → CURRENT.set(...)    ProfileReloadListener.java:58
```

**逐句对照**

- `AddReloadListenerEvent`　原版在每次资源重载时广播这个事件，让模组挂上自己的重载监听器。
- `└─ AdventureEvents.addReloadListeners`　模组在这里把监听器加进重载队列。
- `└─ new ProfileReloadListener()`　构造一个"作者档案"监听器；它继承 `SimplePreparableReloadListener`，因此工作被分成 `prepare`（可在后台线程做的解析）与 `apply`（必须回主线程的赋值）两段。
- `├─ prepare(ResourceManager, ProfilerFiller)`　解析阶段入口，参数是资源管理器与性能分析器。
- `│   ├─ resources.getResourceStack(default.json)`　按固定路径取出**资源的整条覆盖栈**（内置资源在最底、数据包在上）。
- `│   ├─ 检查栈深度 ≤ 2（内置 + 至多一个数据包）`　多于两个来源就无法判断谁该生效，直接报 `CONFIG_CONFLICT`。
- `│   ├─ AdventureWorldConfigParser.parse(reader)`　解析选中的那一份 JSON 文本，产出不可变的 `AdventureWorldConfig`。
- `│   ├─ CanonicalConfigJson.write(config)`　把配置写成**键序固定、无多余空白**的规范 JSON。
- `│   └─ AtomicPlanRepository.sha256(canonical)`　为规范 JSON 求 sha256，作为这份配置自身的身份。
- `└─ apply(LoadedProfile, ...) → CURRENT.set(...)`　主线程阶段把结果发布到静态读取点。

产物 `LoadedProfile`（`config/LoadedProfile.java`）是记录：profile id、解析后的 `AdventureWorldConfig`、规范 JSON、规范 JSON 的 sha256、来源数据包 id。
`ProfileReloadListener.current()` 是全局读取点（`ProfileReloadListener.java:61`），未加载完就抛 `IllegalStateException`。

链条要点：

- **只有内置资源 + 至多一个覆盖数据包**这一种无歧义组合，超过两个来源直接 `CONFIG_CONFLICT`。
- 规范 JSON 的 sha256 参与计划身份，所以**改一个作者字段就作废已有 READY 计划**。

### 3.3 服务器启动：先算计划，再让游戏继续

`AdventureEvents` 挂五个事件，顺序由 NeoForge 生命周期决定，且**故意重复调用同一个幂等入口**：

```text
ServerAboutToStartEvent    → serverAboutToStart      AdventureEvents.java:41
    ├─ 取 LevelStem.OVERWORLD 的生成器（不是 AdventureChunkGenerator 就直接返回）
    ├─ ProfileReloadListener.current()                AdventureEvents.java:47
    ├─ new ContentPreflight().validate(config, RegistryLookup, adapters)   AdventureEvents.java:51
    └─ RuntimePlanRegistry.start(planKey, () -> RuntimePlanner.plan(...))  AdventureEvents.java:66

ServerStartingEvent        → serverStarting          AdventureEvents.java:70
    └─ RuntimePlanRegistry.start(...).join()          AdventureEvents.java:78
        └─ server.overworld().setDefaultSpawnPos(plan.spawnPosition())     AdventureEvents.java:81

LevelEvent.Load            → levelLoaded             AdventureEvents.java:85
    └─ RuntimePlanRegistry.start(...).join()          AdventureEvents.java:92  ← 普通世界首个区块搜索前的最后一道屏障

LevelEvent.CreateSpawnPosition → createSpawn         AdventureEvents.java:97
    └─ RuntimePlanRegistry.await(planKey)             AdventureEvents.java:100
        → event.setSpawn(...) + event.setCanceled(true)
        （取消原版出生点搜索，改用计划里的冻结出生点）

ServerStoppedEvent         → serverStopped           AdventureEvents.java:107
    └─ RuntimePlanRegistry.clear()                    AdventureEvents.java:108
        （同时清 PlanningProgress）
```

**逐句对照**

- `ServerAboutToStartEvent → serverAboutToStart`　服务端即将启动、还没构造 `ServerLevel` 时触发，模组在这里做准备并**启动**规划任务。
- `├─ 取 LevelStem.OVERWORLD 的生成器`　从维度注册表里看主世界用的是不是本模组的生成器；不是就直接返回，装了这个模组但换用别的世界类型时不产生任何副作用。
- `├─ ProfileReloadListener.current()`　取上一节解析好的作者档案。
- `├─ new ContentPreflight().validate(...)`　内容预检：配置里引用的每个群系与结构都必须存在于注册表、且都有可用适配器，否则在这里就失败，不会等到生成区块时才发现。
- `└─ RuntimePlanRegistry.start(...)`　**启动**规划：第一次调用真正把任务丢到规划线程池，之后重复调用只是取同一个 future。
- `ServerStartingEvent → serverStarting`　服务端对象已存在、准备进入启动流程。
- `└─ start(...).join()`　取计划并**阻塞等待**完成。
- `└─ server.overworld().setDefaultSpawnPos(...)`　把计划冻结的出生点写进世界设置。
- `LevelEvent.Load → levelLoaded`　主世界已加载但原版还没搜索出生区块；这一次 join 是出生区块生成前最后的屏障。
- `LevelEvent.CreateSpawnPosition → createSpawn`　原版即将搜索出生点。
- `└─ RuntimePlanRegistry.await(planKey)`　此时计划必然已就绪（前面 join 过），所以只是取值。
- `→ event.setSpawn(...) + event.setCanceled(true)`　写入计划的坐标与朝向，并**取消**原版搜索，避免把玩家放到计划之外。
- `ServerStoppedEvent → serverStopped`　服务端停止。
- `└─ RuntimePlanRegistry.clear()`　清空计划表与进度快照，让下一个会话从干净状态开始。

四个入口都调用 `RuntimePlanRegistry.start(...)`，而它内部是

```java
PLANS.computeIfAbsent(profile, ignored -> CompletableFuture.supplyAsync(planner, PLANNERS));
```

`RuntimePlanRegistry.java:32`。也就是说：**第一次触发真正开始规划，后续触发只是拿同一个 future**。这解释了为什么同一个 lambda 被抄了四遍——它们在语义上必须完全等价，重复出现在这里而不是抽成公共方法，是为了让每个事件点都显式说明“我依赖计划已就绪”。

两处注释记录了为什么这样排序（`AdventureEvents.java:63-65`、`AdventureEvents.java:38`）：不能在 `ServerAboutToStartEvent` 里 join，因为此时 Minecraft 还没创建 `ChunkProgressListener`，客户端加载界面无法渲染；屏障放在首次群系/区块查询和 `LevelEvent.Load` 上，加载界面正好覆盖规划时间。客户端那个界面就是 `client/PlanningLoadingOverlay.java`，它读 `runtime.PlanningProgress.current()`（`PlanningLoadingOverlay.java:20`）——**这是客户端唯一与规划会话的耦合点**。

**逐句对照**

- `RuntimePlanner.plan(seed, loaded, worldDirectory, adapters, pieceSupport)`　规划的公开入口。五个参数分别是世界种子、解析好的作者档案、存档根目录（计划与指标写到它下面）、适配器集合、以及"本环境能否重建冻结部件"的查询回调。
- `├─ PlanningProgress.begin(profile)`　开一次进度运行；它只是给加载界面看的快照，不参与生成。
- `├─ PlanIdentity.hash(seed, loaded, adapters)`　算出本次规划的输入指纹。公式右边列出了它的全部组成：规范 JSON（作者配置）、种子、算法版本、实现修订号、水文版本、地形版本、适配器版本键、代价版本、侵蚀版本。**任何能改变生成结果的输入都必须出现在这里**，因为下一步拿它判断磁盘上的计划还算不算数。
- `├─ ① 命中 READY？`　先查存档里有没有与这份指纹匹配的现成计划。
- `│   ├─ repository.loadReady(worldDirectory, id, inputHash)`　读计划目录。
- `│   ├─ manifest.json 四个字段全等`　清单里恰好四个字段：格式版本、profile、输入指纹、载荷指纹；前三个必须全等。
- `│   ├─ payload sha256 校验 → gzip 解压 → 规范 JSON`　先校验载荷字节的指纹，再解压得到规范 JSON 文本。
- `│   └─ codec.decode(...)`　把规范 JSON 解回 `PlanSnapshot` 冻结数据。
- `│       └─ GeneratedAdventurePlan.restore(config, snapshot)`　用冻结数据重建可查询的计划对象。
- `│           ├─ 重建地形栈 PlanTerrain.assemble(...)`　按固定顺序重新拼出区域 → 岛面 → 侵蚀 → 水文 → 形态这条链。
- `│           ├─ 校验 recipeSettings`　冻结的地形配方设置必须与当前 profile 一致，否则拒绝。
- `│           └─ 校验 recipeRegions`　冻结的区域配方清单必须与重新算出来的一致，防止悄悄换个区域布局。
- `│   └─ checkFrozenPieces(plan.structures(), pieceSupport)`　逐个冻结部件确认本环境注册了它的类型——检查通过才算真正可用。
- `│   → 命中就 return，一跳都不重算`　这就是 READY 路径的全部工作：没有海岸、没有侵蚀、没有水文、没有群系求解。
- `├─ ② 预算三个半径`　没命中 READY，才进入首次规划。这里先算三个用于保留空间的半径。
- `│   radius`　作者配置的大陆半径。
- `│   spawnRadius = min(256, radius/10)`　出生点周围要留空的半径。
- `│   spawnFootprint`　出生结构自身需要的占地半径（由适配器声明 + 出生点偏移）。
- `│   keep`　两者之和再加一点余量，交给海岸生成，保证出生点与出生结构不会被海切掉。
- `├─ ③ progress.stage(COAST) → CoastGenerator(V2).generate(...)`　生成一条共用的大陆边界折线。
- `│   → Coastline（顶点串）+ landBand + seaBand`　产物是不可变折线，外加陆侧与海侧的过渡带宽度。
- `├─ ④ TerrainCapacitySolver.reserve(...)`　把作者的群系与高度需求换算成地形"容量预留"。
- `│   → TerrainCapacityPlan`　产物是冻结的预留结果；后面的地形只消费它，不再自己求解配额。
- `├─ ⑤ PlanTerrain.foundation(...)`　建地形的两个底层：区域采样器与岛面。
- `│   ├─ new RegionTerrain(...)`　区域采样器：世界对齐的抖动 Voronoi 区域，每个区域一个模板与一个具体配方；它消费上一步的容量预留与作者的填充规则。
- `│   └─ new IslandMacroTerrain(...)`　岛面：把海岸距离与区域高度合成陆侧高度，海侧按水深场下潜。
- `├─ ⑥ progress.stage(EROSION) → ErosionGenerator(...).generate(...)`　算侵蚀增量场（规划期一次性算好、冻结）。
- `│   → ErosionDeltaField`　产物是按 8 格间距栅格化的高度增量。
- `│   └─ terrainFoundation.eroded(erosion) → ErodedTerrain`　把岛面裹上一层"叠加增量"的地形，供水文与后续阶段读取。
- `├─ ⑦ progress.stage(RIVERS) → HydrologyGenerator(...).generate(...)`　在**已侵蚀**的岛面上生成河网。
- `│   → RiverNetwork`　产物是河道折线、逐点水位与湿地。
- `├─ ⑧ PlanTerrain.compose(...).withMemoizedQueries()`　把地形栈拼完整，并加一层缓存包装。
- `│   → HydrologyTerrain → TerrainMorphology → ExactGridTerrain`　顺序是：水系雕刻 → 形态测量 → 半方块记忆化包装。
- `├─ ⑨ progress.stage(COSTS) → CostPlanner(V2).build(...)`　从出生点建代价场。
- `│   → 16 格有向代价图 + CostDistanceMap + normalizedPreferenceAt`　产物是完整的有向代价图与一次 Dijkstra 结果，用来把"离海岸多远"折算成 0–10 的冒险等级。
- `├─ ⑩ progress.stage(PLACEMENT) → new JointPlanner(V2).plan(...)`　联合求解群系地块、结构与出生点。
- `│   ├─ StructureAdapterBridge(adapters, terrain) 作为 StructureFreezer`　结构桥：规划器提出需求，桥把它变成冻结的结构实例。
- `│   ├─ LevelConstraint：AdventurePreference.penalty(...)`　等级约束：把"请求等级与实际等级之差"折算成软惩罚。
- `│   └─ BiomeConstraint：(biome,x,z) -> adapters.biome(biome).compatibility(...).allowed()`　群系约束：某个群系能不能放在某个坐标，最终要问它的适配器。
- `│   → joint.patches() / joint.structures() / joint.spawn()`　产物：群系地块、结构实例、出生点。
- `├─ ⑪ GeneratedAdventurePlan.fromPlanning(...)`　把这一轮的产物冻结成计划对象。
- `│   ├─ 冻结输入：seed、config、coastline、rivers、band、terrainVersion、spawn、patches、structures、diagnostics、erosion、capacities`　这些是写进 plan-v2 文档的全部内容。
- `│   └─ PlanningInputs(planningTerrain, jointPlanner.climate())`　把**刚算过的**地形栈与温度场直接递给计划对象复用，避免为了"结构整洁"再采样一遍。
- `├─ ⑫ MinimumAreaPolicy.checkAchievedAreas(...)`　终检已达的干燥面积是否还满足作者要求。
- `│   → 放宽项写 warn 日志；把已达面积压到下限以下则抛 NO_SOLUTION_IN_DOMAIN`　面积不足只警告，但边界混合把已达面积又压小了就是硬失败。
- `├─ ⑬ checkFrozenPieces(plan.structures(), pieceSupport)`　**发布前**再查一次冻结部件：任何一个部件在本环境没有注册类型，计划就不发布。
- `└─ ⑭ progress.stage(SAVE)`　保存阶段。
- `　　repository.publishAtomically(..., codec.encode(...))`　把快照编码成规范 JSON，然后原子发布（临时目录 → fsync → 改名 → 最后写 READY）。
- `　　metrics.write(...) → planning-metrics.json`　另外写一份计时与统计，它不进计划字节、也不进输入身份。

阶段与进度百分比由 `plan.PlanningStage` 的枚举顺序决定（`plan/PlanningStage.java`）：`CACHE 0-2, COAST 2-8, EROSION 8-46, RIVERS 46-55, COSTS 55-75, PLACEMENT 75-78, TEMPERATURE 78-80, HUMIDITY 80-81, SEEDS 81-84, GROWTH 84-89, STRUCTURES 89-90, FILLER 90-94, TRANSITION 94-95, VALIDATION 95-98, SAVE 98-100`。`PlanningProgress.Run.update` 会拒绝倒退（`PlanningProgress.java:37`）。

两条与性能相关的设计决定，代码里都写了理由：

- ⑧ 的 `withMemoizedQueries()` 只给首次规划用；READY 恢复读的是原始 `TerrainMorphology`。注释明确说这是“已接受的优化”，并用 `PlanTerrainTest` 钉住两条路径对同样的坐标给出相同答案（`PlanTerrain.java:411`）。
- ⑪ 复用了第 ⑧ 步已经算热的地形栈与 `JointPlanner` 刚建好的 `ClimatePlan`，避免第二次采样（`PlanAssembly.java:19`、`GeneratedAdventurePlan.java:91`）。

### 3.5 持久化：READY 最后落盘的原子发布

```text
world/adventureworldgen/plans/adventureworldgen_default/
 ├─ .adventureworldgen_default.tmp-<uuid>/   ← 临时目录（同文件系统）
 │   ├─ plan.json.gz        canonical JSON 的 gzip
 │   ├─ manifest.json       {format, input_sha256, payload_sha256, profile}
 │   └─ READY               空文件，最后写
 └─ （原子改名后成为正式目录）
```

**逐句对照**

- `world/adventureworldgen/plans/adventureworldgen_default/`　计划落在存档目录下的这个路径；最后一段目录名把 profile id 里的 `:` 与 `/` 换成 `_`。
- `├─ .adventureworldgen_default.tmp-<uuid>/`　发布期间真正写入的临时目录，带随机后缀；它必须与目标**在同一个文件系统**上，否则改名不是原子的。
- `│   ├─ plan.json.gz`　载荷：规范 JSON 的 gzip 压缩。
- `│   ├─ manifest.json`　清单：格式版本、输入指纹、载荷指纹、profile。恰好四个字段。
- `│   └─ READY`　零字节标记文件，**最后**写；它存在才代表这个目录可以读。
- `└─（原子改名后成为正式目录）`　`ATOMIC_MOVE` 把临时目录整体改名成正式目录，所以读者要么看到旧状态、要么看到完整新状态。

`AtomicPlanRepository.publishAtomically`（`AtomicPlanRepository.java:59`）的顺序是：写 payload → 写 manifest → 写 `READY` → `forceDirectory(临时目录)` → `Files.move(..., ATOMIC_MOVE)` → `forceDirectory(parent)`；每个文件都用 `channel.force(true)` 且把 mtime 置零（`:112`），保证字节级可复现。

`loadReady`（`:36`）的判据是：`READY` 存在、manifest 恰好 4 个字段且三者全等、`payload_sha256` 与实际字节相符。**任一不符都返回空并重新规划**，而不是失败——`READY` 不存在是最常见的“首次启动”情形。

同一个 input hash 但字节不同会直接报错：`a different READY plan already exists for the same input hash`（`:67`）。也就是说 input hash 是不可变契约，不是缓存键。

`PlanV2Codec`（`persistence/PlanV2Codec.java:39`）的顶层键被 `Set.of(...)` 固定为 `algorithm, format, hydrology, input_sha256, operation_counts, profile, random_keys, seed, spawn, terrain, structures, biome_layout`；解码时对每个子对象都用允许键集合校验（`:87`、`:103`、`:110`、`:113`），未知键即报错。`random_keys` 是一个纯记录用的字符串数组（`:66`），列出这份计划用到的随机键前缀。

### 3.6 区块生成：一次请求的完整路径

`AdventureChunkGenerator` 继承原版 `ChunkGenerator`，内部持有**两个原版委托**：`vanillaDelegate`（主世界 noise settings，负责雕刻与刷怪）和 `oceanDelegate`（自定义 `adventureworldgen:ocean` settings，只用于海底原生洞穴与含水层）。所有入口的第一句都是同一个屏障：

```java
var plan = (GeneratedAdventurePlan) RuntimePlanRegistry.await(planKey());
```

- `最后 Heightmap.primeHeightmaps(4 种高度图)`　重算四种高度图，否则后续结构与生物会把地形判断错。
- `② createBiomes(...) → AdventureBiomeSource.getNoiseBiome(...)`　原版在四分格分辨率上问"这里是什么群系"。
- `└─ RuntimePlanRegistry.await(...).biomeAt(...)`　转问计划；计划给出 `ContentId`，再换成注册表里的群系句柄。
- `③ createStructures(registries, state, manager, chunk, templates)`　结构阶段。
- `├─ super.createStructures(...)`　**先**让原版照常生成非受控结构。
- `├─ 对 plan.controlledStructureIds() 逐个把该结构在本区块的 start 置为 INVALID_START`　再把受本模组控制的结构在此处的原版候选**擦掉**，避免同一结构出现两次。
- `└─ 对 plan.structuresIntersecting(...) 中起点在本区块的结构`　只有起点落在本区块的计划结构才在这里注入，保证一座结构只注入一次。
- `└─ new StructureStart(..., new PiecesContainer(FrozenPieceRestore.restore(...)))`　把冻结的部件按注册表里的类型重建，然后交给原版的 `StructureStart`——之后的下沉、放置都是原版流水线在做。
- `④ buildSurface(region, structures, randomState, chunk)`　表面阶段（草皮、沙子等表层材料）。
- `└─ buildPlannedSurface(region.registryAccess(), chunk)`　走我们自己的表面流程。
- `├─ 先快照 256 列 OCEAN_FLOOR_WG 高度`　表面规则会反复查列高，先缓存下来，避免为每一格重算 384 格高的一列。
- `├─ PlannedSurfaceNoiseChunk(...)`　一个只覆写 `preliminarySurfaceLevel` 的噪声上下文，让原版表面规则看到的是**我们合成的地形**，而不是另一套噪声世界。
- `├─ BiomeManager 用 plan.seed() 的混淆种子`　表面规则会用群系来决定表层材料，这里保证它问到的群系与计划一致。
- `└─ state.surfaceSystem().buildSurface(...)`　实际刷表层；规则本身来自注册的主世界 noise settings（也就是数据包能改的那一份），本模组不覆写材料。
- `⑤ applyCarvers(...)`　雕刻阶段（洞穴、峡谷）。
- `├─ 区块内有受控结构 → 直接返回`　有计划结构的地方不雕刻，避免把结构地基掏空。
- `├─ 24×24 范围（步长 4）内任一点 wet() → 直接返回`　有自绘水面的区块不雕刻：原版的含水层会把这些河面湖面抽干。
- `└─ 否则 vanillaDelegate.applyCarvers(...)`　其余区块交给原版。
- `⑥ spawnOriginalMobs(region)`　原版刷怪，纯委托。

高度查询走完全独立、且不重算列的路径：`getBaseHeight`（`:245`）与 `getBaseColumn`（`:259`）都只读 `plan.terrainAt` / `plan.solidSurfaceAt`，海列再借 `oceanDelegate.getBaseColumn` 拿原生洞穴。`addDebugScreenInfo`（`:283`）把地形版本、实现修订号、区域、模板、配方、复合权重、坡度、起伏打进 F3。

### 3.7 运行时查询：一次 `biomeAt` 的决策顺序

区块与群系的所有查询最终落到 `GeneratedAdventurePlan` 的方法上。`biomeAt` 是最热的一个：

```text
GeneratedAdventurePlan.biomeAt(blockX, blockY, blockZ)          GeneratedAdventurePlan.java:220
 ├─ 坐标先对齐到未扭曲的四分格中心：floorDiv(v,4)*4 + 2        ← 注释说明：扭曲后再取整会产生梳状混叠
 ├─ columnBiomes（16384 项 LRU-ish 缓存）命中即返回
 └─ uncachedBiomeAt(x, z)                                       GeneratedAdventurePlan.java:229
     ├─ MacroSample = terrain.sample(x, z)（= Morphology → Hydrology → Erosion → Island）
     ├─ OCEAN → minecraft:ocean
     ├─ mixedLandBiomeAt(x, z, sample)                           GeneratedAdventurePlan.java:243
     │   ├─ landBiomeAt：先扫 biomePatches（规划器给的必需/可选斑块）
     │   │               未命中则 filler.biomeAt(x,z,sample)（冻结的填充网格）
     │   └─ 三个“禁止混合”条件直接返回 fallback：
     │       · 该 patch 在 blendProtectedPatches 里（面积保护）
     │       · 距出生点 ≤ 32 格
     │       · 落在某结构的 biomeProtection 盒内
     │   └─ 否则 blockBlend.sample(..., legal = config.biomes().allows(id,sample)
     │                                        && environmentRules.allows(id,x,z,sample))
     │       ← 本地域扭曲：把归属查询挪到邻近坐标，但合法性仍按当前点判定
     └─ RIVER / LAKE → VanillaWaterBiomes.inlandWaterFor(land)   compat/vanilla/VanillaWaterBiomes.java:134
```

**逐句对照**

- `GeneratedAdventurePlan.biomeAt(blockX, blockY, blockZ)`　"这个方块坐标是什么群系"，整条区块与群系查询最终都落到这里。
- `├─ 坐标先对齐到未扭曲的四分格中心：floorDiv(v,4)*4 + 2`　先把坐标吸附到一个 4 格单元的中心。注释说明为什么必须这样：先扭曲再取整会让单元大小不均、出现梳齿状混叠。
- `├─ columnBiomes（16384 项缓存）命中即返回`　命中缓存就直接返回，这是热路径上最省事的一步。
- `└─ uncachedBiomeAt(x, z)`　未命中才真正判定。
- `├─ MacroSample = terrain.sample(x, z)`　问地形栈要这一列的地形观测（形态 → 水文 → 侵蚀 → 岛面，逐层向下）。
- `├─ OCEAN → minecraft:ocean`　海直接是原版海洋群系。
- `├─ mixedLandBiomeAt(x, z, sample)`　陆地群系要先定归属、再做边界混合。
- `│   ├─ landBiomeAt：先扫 biomePatches`　先看规划器给的斑块是否覆盖这一点。
- `│   │   未命中则 filler.biomeAt(x,z,sample)`　否则读冻结的填充网格。
- `│   └─ 三个"禁止混合"条件直接返回 fallback`　下面三种情况不做混合，保持原样：被面积保护、离出生点太近、落在结构的群系保护盒里。
- `│       · 该 patch 在 blendProtectedPatches 里（面积保护）`　已达面积不足的斑块不能被混合再削小。
- `│       · 距出生点 ≤ 32 格`　出生点周围保持确定的群系（结构依赖它）。
- `│       · 落在某结构的 biomeProtection 盒内`　结构周边的群系由结构说了算。
- `│   └─ 否则 blockBlend.sample(...)`　其余地方做本地域扭曲混合。
- `│       ← 本地域扭曲：把归属查询挪到邻近坐标，但合法性仍按当前点判定`　挪过去问"那里是什么群系"，但如果挪到的位置不合法就退回原值——这样边界被弯曲，却不会把非法群系带进来。
- `└─ RIVER / LAKE → VanillaWaterBiomes.inlandWaterFor(land)`　河流与湖泊不新建群系，而是按脚下陆地群系换成对应的水群系（寒冷陆地换冻河）。

`BiomeEnvironmentRules.allows`（`biome/BiomeEnvironmentRules.java:236`）是“这里能不能放这个群系”的唯一答案：温度类型准入 + 湿度准入 + `shoreOnly` 规则 + 海岸优先规则。它读 `ClimatePlan` 与 `HumidityPlan`，但**不生成任何一个场**，也不持有搜索状态——这正是 `biome → climate` 单向边成立的原因。

### 3.8 结构从注册到落地：一条不留分支的链

```text
第三方/内置注册
 └─ api.AdapterRegistrations.register(BiomeAdapter|StructureAdapter)   api/AdapterRegistrations.java:14,18

     └─ worldgen.RegisteredPieceSupport.INSTANCE                 worldgen/RegisteredPieceSupport.java:20

```

**逐句对照**

- `第三方/内置注册`　支持一个结构的第一步是注册，而不是改核心。
- `└─ api.AdapterRegistrations.register(BiomeAdapter|StructureAdapter)`　第三方模组在早期把自己写的适配器交进来。
- `（第一次 freeze() 之后注册直接抛 IllegalStateException）`　注册在第一次预检前原子关闭，之后不再接受新注册——避免"计划已经开算又冒出一个适配器"。
- `内置装配`　模组自己那一批适配器在这里组装。
- `└─ MinecraftAdapters.builtIn()`　返回冻结后的适配器索引。
- `├─ AdapterRegistry.builder(new GenericBiomeAdapter())`　先放一个通用兜底：没写适配器的普通群系走它。
- `├─ + vanilla ocean 的匿名 BiomeAdapter`　海洋群系。
- `├─ + VanillaRiverBiomeAdapter(river / frozen_river)`　两条原版河群系。
- `├─ + VanillaDesertPyramidAdapter`　v1 唯一支持的原版结构。
- `└─ + AdapterRegistrations.freeze() 的外部注册`　再并入第三步注册进来的第三方适配器，按 id 排序保证顺序确定。
- `规划期`　计划阶段真正使用适配器。
- `└─ StructureAdapterBridge.freeze(demand, x, y, z, structureSeed)`　规划器说"我要一座某结构"，桥负责把它变成冻结实例。
- `├─ adapters.structure(id).orElseThrow(UNSUPPORTED_CONTENT)`　没有适配器就直接失败，不会静默跳过这座结构。
- `├─ 从 describe().rotations() 里按 structureSeed 取旋转`　旋转由结构自己的种子决定，可复现。
- `├─ adapter.prepare(Candidate(...), structureSeed)`　适配器在这一步把结构"冻结"：算出全部部件与它们的规范 NBT。
- `├─ adapter.validatePrepared(prepared, terrain) 非空即 NO_SOLUTION_IN_DOMAIN`　适配器自己检查这块地能不能放（湿不湿、地面高差多大），返回的错误列表非空就换地方。
- `└─ → AdventurePlanView.PlannedStructure`　产物是带部件字节的冻结结构。
- `发布前自检`　写盘之前必须确认这些冻结部件在当前环境里重建得出来。
- `└─ RuntimePlanner.checkFrozenPieces → FrozenPieceSupport.firstUnsupported`　逐个部件问"有没有未注册的类型"。
- `└─ worldgen.RegisteredPieceSupport.INSTANCE`　生产环境的回答：看游戏注册表。
- `└─ FrozenPieceRestore.frozenPieceType(nbt) + registeredPieceType(type)`　先从 NBT 里读出类型 id，再查这个 id 有没有注册。
- `执行期`　真正生成区块时。
- `└─ AdventureChunkGenerator.createStructures → FrozenPieceRestore.restore`　在结构起点所在区块重建部件。
- `└─ BuiltInRegistries.STRUCTURE_PIECE.get(id).load(context, tag)`　用**与原版相同的注册表**找到部件类型，让它自己从 NBT 恢复——所以核心不需要认识任何具体结构。

这条链的每一环都只认“注册表里有没有这个 id”，**核心从不认识任何具体结构**。`FrozenPieceRestore` 的类注释解释了与香草实现的差异：原版 `PiecesContainer.load` 遇到无法重建的部件会记日志并丢弃（存档必须能开），而计划是承诺，所以这里直接硬失败并报出部件 id、部件号与实例号（`FrozenPieceRestore.java:25`）。

## 5．逐包展开

### 5.1 `plan`：被所有层引用的词汇

`plan` 是依赖图底部，16 个文件里没有一行 Minecraft 代码。它分四类内容：

**身份与版本**

| 类型 | 说明 |
|---|---|
| `ContentId` | `namespace:path` 的强校验记录（正则 + 单冒号），**不做注册表查询**；`Comparable`，全项目用它当集合键与排序键 |
| `PlanVersions` | `HYDROLOGY = "ftf-hydrology-adapted-v2"`；注释明确这不是计数器而是契约名 |
| `PlannerProfile` | 全部不可由作者调的常量：算法/格式/水文版本、面积单元（`AreaGrid.CELL_SIDE` 与 16/8/4 三档）、代价格距（16/8）、容差 0.35、`Terrain`/`Coast`/`Search` 三组参数；`PlannerProfile.V2` 是唯一实例 |
| `TemperatureType` | `VERY_COLD / COLD / MEDIUM / HOT`；放在 `plan` 是因为冻结气候状态要存它，而 `config` 已经依赖 `plan` |
| `StableIds` | `required/<i>`、`patch/required/<i>`、`instance/<结构 id>/<序号>`、`patch/carrier/<实例>`、`patch/spawn` |

**规划产物**

| 类型 | 说明 |
|---|---|
| `PlannedBiomePatch` | 一块群系归属：id、群系、冒险等级、包围盒、可选 `CellMask`、锚点。构造器校验“非空包围盒”“锚点在掩码内”“掩码格必须在包围盒内”；无掩码时 `contains` 走一个**基于 patchId 哈希相位的三正弦不规则闭合轮廓**（`PlannedBiomePatch.java:47`） |
| `PlanningFailure` | 七个 `Code`：`CONFIG_CONFLICT / UNSUPPORTED_CONTENT / RESOURCE_LIMIT / SEARCH_BUDGET_EXHAUSTED / PRECISION_INSUFFICIENT / NO_SOLUTION_IN_DOMAIN / EXECUTION_FAILED`；诊断 map 用 `TreeMap` 规范化，保证错误文本可复现、可持久化 |
| `PlanningObserver` / `PlanningStage` | 观察者只读契约 + 15 个阶段及其进度区间；注释要求实现**不得**影响重试、随机输入、遍历顺序、预算或回退 |
| `PlanDiagnostics` | 海岸顶点、河道、河点、侵蚀样本/操作、代价节点/边、联合操作计数 + 地形版本；`basic(...)` 给“贵阶段之前就能数出来”的计数用 |

**冻结环境状态**（全部带“组件名与顺序属于持久化格式”的注释，反射序列化进 `biome_layout`）

`BiomeLayout(ClimateState, FillerState, List<String> protectedPatches)` 是三段的容器：
`ClimateState` 有 16 个组件（两个模糊高度场、角度、低/高、三个阈值、雪线标志、出生带、需求/实际比例数组、旧修正列表、供给列表、`HumidityState`、温度场版本）；`FillerState(extent, labels[], seedCount)` 是填充归属网格；`HumidityState` 存两套距离场、水位、达成比例与天气偏移。

**为什么这些状态在 `plan` 而不在 `climate`/`planner`**：`ClimateState` 里出现 `TemperatureType`，而 `config` 已经依赖 `plan`；反过来让冻结状态引用作者模型就会形成环。仓库里 `TemperatureType.java` 的注释把这个理由写明了。

### 5.2 `spatial`：四个无依赖基础件

| 类型 | 职责与要点 |
|---|---|
| `Vec2` | 二维只读点，`distance` 等几何方法 |
| `AreaGrid` | 面积网格的单元边长常量（`CELL_SIDE`），被 `PlannerProfile` 引用 |
| `CellMask` | **四分格（4 格）稀疏归属**：`long[]` 排序去重，重复格直接抛错；`key(x,z)` 把格坐标打包进 long；`encode()/decode()` 用 Base64 直接存 `long` 序列，解码上限 64 MB；`CellMaskTest` 钉住往返一致 |
| `ColumnQueryCache<T>` | 定长 2 的幂、无锁记忆化：SplitMix64 哈希取槽，槽内比对完整 key，冲突只覆盖不链化；**并发未命中会重复计算，但不在地形工作上加锁**（`ColumnQueryCache.java:178`） |

`CellMask` 的格坐标约定贯穿全局：所有权格中心是 `floorDiv(v,4)*4 + 2`，`GeneratedAdventurePlan.biomeAt` 第一句就是它。

### 5.3 `noise`：确定性随机源

| 类型 | 机制 |
|---|---|
| `DeterministicRandom` | 分层的随机契约：`digest/seed/sample(worldSeed, algorithmVersion, stage, stableId, operationIndex)` 用 **SHA-256** 摘要再取前 8 字节（`sample` 取高 53 位映射到 `[0,1)`，`seed` 取整 64 位）；`mix(x)` 是 SplitMix64 finalizer，用于“便宜且确定”的排序与抖动。类注释声明改常量或位移就是改契约 |
| `ValueNoise` | 世界对齐的二维值噪声：格点值由 `SHA-256(worldSeed ‖ fieldId)` 得到初始 key，格内用 `mix64` 混合，双线性 + smoothstep 插值，输出 `[-1,1]`；`fastFloor` 处理负坐标 |
| `GradientNoise` | 同一 key 派生方式的梯度噪声，供温度场使用（key 里的 stage 是 `"terrain-r5"`，保留自早期版本） |
| `ContinuousDomainWarp` | 三层可逆位移（尺度 512/160/64，幅度 64/12/8）连续施加 4 步，`strength ∈ [0,1]`；注释给出理由：单次大偏移会折叠坐标，小步位移在 `∞-范数 < 0.49` 时保持单射且保向 |

### 5.4 `config`：作者意图的解析与校验

包内 7 个文件，零 Minecraft 依赖。职责边界很干净：**只做“文本 → 不可变模型 + 语义错误”**。

```text
AdventureWorldConfigParser.parse(Reader)          config/AdventureWorldConfigParser.java（537 行）
 └─ → AdventureWorldConfig                        config/AdventureWorldConfig.java
      ├─ WorldSettings(radius, TerrainSettings)
      ├─ SpawnSettings(biome, SpawnStructure(id, spawnPoint))
      ├─ BiomeSettings(required[], filler[], terrainRules{}, blendRadius=4)
      └─ StructureSettings[]（每项：id, adventureLevel, CountRange, AllowedBiomes, PlacementMode, Spacing, Vec3d entrance）
```

**逐句对照**

- `AdventureWorldConfigParser.parse(Reader)`　解析入口，吃的是 profile JSON 的字符流。
- `└─ → AdventureWorldConfig`　产物是不可变、已规范化的作者配置根对象，下面四项是它的组成部分。
- `├─ WorldSettings(radius, TerrainSettings)`　世界层级设置：大陆半径，以及地形配方设置（12 个配方的权重与形状参数、是否复配、是否启用山脉走廊）。
- `├─ SpawnSettings(biome, SpawnStructure(id, spawnPoint))`　出生设置：期望的出生群系，以及可选的出生结构（结构 id 与相对出生点）。
- `├─ BiomeSettings(required[], filler[], terrainRules{}, blendRadius=4)`　群系设置：必需群系列表、填充群系池、每个群系的准入与评分规则，以及边界混合半径。
- `└─ StructureSettings[]`　结构设置列表，每项含 id、冒险等级、数量区间、允许的承载群系与面积、放置模式、间距区间、入口相对坐标。

作者模型里有三个**派生方法**，它们是“作者语义 → 算法输入”的桥：

| 方法 | 给谁用 |
|---|---|
| `temperaturePreferences(id)` | `BiomeEnvironmentRules` 与 `ClimatePlan`（未声明则 `TemperatureType.unrestricted()`） |
| `fillerWeight(id)` | 填充候选排序与播种（默认 1） |
| `fillerTerrainPolicy()` | **`terrain` 唯一能看到的作者信息**：返回单方法接口 `FillerTerrainPolicy`，只回答“这两种配方能否在同一个填充群系里相遇”。这正是 `terrain → config` 那条环被切断的方式 |

`TerrainRule` 是字段最多的一层（16 个组件）：允许的地形类别、高度上下界、温度等级与四带权重、偏好高度与惩罚系数、填充权重、冒险等级、湿度权重、`shoreOnly`、允许模板、地貌集合。它的紧凑构造器做全量校验，`accepts(MacroSample)` 与 `heightCost(height)` 是两个被 `biome` 与 `planner` 复用的纯查询。

`ContentPreflight`（`config/ContentPreflight.java:15`）是**跨层校验**：它接受调用方注入的 `RegistryLookup`（`biomeExists` / `structureExists` / `snowyAtSeaLevel`），所以既能被生产路径调用（`AdventureEvents` 用注册表实现），也能被单元测试用假实现调用。它检查的内容：

1. 配置里出现的每个群系 id（含硬编码的 `minecraft:ocean`、`minecraft:river`、`minecraft:frozen_river`）必须在注册表里存在，且有适配器（或通用回退）。
2. 每个结构 id 必须存在、必须有适配器，且适配器必须声明 `canFreezeAllPieces()`——**不能冻结全部部件的适配器在预检就被拒**，不会走到发布一半才失败。

`LoadedProfile(id, config, canonicalJson, configHash, sourcePack)` 是解析终点，也是“配置身份”的载体：`canonicalJson` 进 `PlanIdentity.hash`。

### 5.5 `persistence`：只认识冻结数据

三个文件，是 `runtime` 与磁盘之间唯一的桥，且**不引用 `runtime`**（否则 READY 恢复时可能顺着编解码器回到布局求解）。

| 类型 | 说明 |
|---|---|
| `PlanSnapshot` | 16 个组件的 record，就是一份 plan-v2 文档的全部内容：`seed, diagnostics, spawn, coastline, riverNetwork, seaSurface, landBand, seaBand, terrainVersion, recipeSettings, recipeRegions, biomePatches, structures, erosion, capacities, biomeLayout`。放在 `persistence` 而非 `plan` 的理由写在类注释里：它引用 `Coastline`/`RiverNetwork`/`ErosionDeltaField`/`TerrainCapacityPlan`，而这些包已经依赖 `plan`，放进去会成环 |
| `PlanV2Codec` | 手写 Gson 编解码（511 行）：顶层键固定集合、每个子对象用允许键集合校验、所有数值走 `finite/positive/exactInt` 之类的严格读取；`biome_layout` 用 Gson 反射序列化整段 `BiomeLayout` |
| `AtomicPlanRepository` | 原子发布与 READY 读取，见 3.5；`sha256(byte[])` 同时被配置身份与载荷校验复用 |

`decode` 的校验顺序值得记下：先 `format`、`algorithm`、`hydrology`、`profile`、`input_sha256` 五项全等，再读内容。任一不符都抛 `PlanningFailure(EXECUTION_FAILED, "plan-load", "READY plan-v2 payload is invalid")`，并带上原始异常信息（`PlanV2Codec.java:120`）。

11 个文件，是全项目最重的一包（1978 行）。它不引用 `runtime`，进度通过 `PlanningObserver` 显式传入。


**逐句对照**

- `RequirementExpander.expandMinimum(config)`　把作者配置展开成"稳定最小需求"，这一步**不做任何空间选择**。
- `└─ → ExpandedRequirements{patches[], structures[]}`　产物是两份需求清单：需要存在哪些群系地块、需要放哪些结构实例。
- `（把作者配置的"必需群系/结构"变成带稳定 id 的需求对象，不做空间选择）`　"稳定 id"指不随解析顺序变化的 id，这样计划与诊断里的名字可复现。
- `JointPlanner.plan(...)`　联合求解入口，下面十一步都是它做的。
- `├─ new PlacementIndex(config, terrain, levelConstraint, adapterConstraint, ...)`　先建候选索引：把地形按 16 格网格预先采样一遍，作为"哪里可能放得下"的粗目录。
- `│   └─ 粗候选目录 + 精确四分采样的惰性缓存`　粗目录之外，再按需缓存精确的四分格采样；用 fastutil 的原始类型表避免装箱。
- `├─ observer.stage(TEMPERATURE)`　进入温度阶段（只影响进度显示）。
- `│   └─ climate = new ClimatePlan(...)`　用索引的缓存采样建温度场，并把需求统计注入进去。
- `├─ rules = new BiomeEnvironmentRules(config, climate)`　建准入服务：从这一刻起，所有"能不能放"的判定都走它。
- `├─ observer.stage(SEEDS) → BiomeAllocationPlanner.allocate(...)`　进入播种与生长阶段，分配群系地块。
- `│   └─ 竞争生长 + 有界多区域回退，环境准入从不放宽 → patches[]`　面积不够时允许用多个不相连的区域凑，但**绝不放松环境准入**（不会为了凑面积把雪群系放到沙漠）。
- `├─ observer.stage(STRUCTURES)`　进入结构阶段。
- `│   └─ 必需结构按"先非出生点、再等级、再 instanceId"排序后逐个 placeRequiredStructure`　排序是为了确定性：同一份配置每次得到同样的尝试顺序。
- `├─ 可选结构：每个尝试要么整块提交，要么保持合法最小解不变`　可选结构是纯优化，失败不影响合法性。
- `├─ spawn = resolveSpawn(config, terrain, structures)`　确定出生点：优先用出生结构给的位置，没有结构就用原点所在列的地面之上。
- `└─ validate(...)`　最后做一次独立复核（自己的访问预算、自己的检查清单）。
- `　　→ Result(patches, structures, spawn, operations)`　返回地块、结构、出生点与操作计数。

`JointPlanner` 里两个细节体现了“结构必须有承载群系”这条约束：必需结构先从 `patches` 里按 `StableIds.carrierPatch(instanceId)` 找到载体斑块，找不到直接抛（`JointPlanner.java:105`）；可选结构失败用 `break` 而不是 `continue`，因为同一结构的尝试是单调加长的，后面只会更难。

两处注释是不变量的原话，值得记住（`JointPlanner.java:99`、`:113`）：必需结构的准备**发生在整份必需群系布局冻结之后**；可选结构实例是软优化，每次尝试要么整块提交、要么让合法最小解原样不动。

必需结构的候选搜索（`placeRequiredStructure`，`:136-186`）分三步长 `{16, 8, 4}`：从载体掩码里按步长取点，过滤掉不平坦与被 `LevelConstraint` 拒绝的点，再按

```text
4 × levelConstraint.penalty(level, x, z)
+ 3 × rules.cost(载体群系, x+2, z+2, sample)
+ 距载体锚点距离 / max(32, √载体面积)
+ 0.35 × DeterministicRandom.mix(salt ^ cell) 的高 53 位
```

**逐句对照**（这个分数越小越优先）

- `4 × levelConstraint.penalty(level, x, z)`　等级代价权重最高（×4）：位置的实际冒险等级与请求等级差得越远越不优先。
- `+ 3 × rules.cost(载体群系, x+2, z+2, sample)`　环境代价（×3）：温度带偏差、硬高度代价与湿度不匹配。
- `+ 距载体锚点距离 / max(32, √载体面积)`　离载体锚点越远越不优先，但用一个与载体尺寸相关的分母做尺度无关化，小载体不会因此失去所有候选。
- `+ 0.35 × DeterministicRandom.mix(salt ^ cell) 的高 53 位`　一个很小的确定性抖动，用来打散并列，保证同种子同结果。
- （平局按格号）　分数完全相同时用格号定序，避免依赖集合迭代顺序。

排序（平局按格号），逐个调用 `freezer.freeze(...)` 并跑一条拒绝链：适配器不得改写实例 id 或原点、footprint 与 biomeProtection 非空、入口被等级接受且在载体内、所有盒都在载体内、与已冻结结构无预留冲突。预备次数上限是 `min(4096, requiredCandidatePreparations)`（生产 4096）。全部耗尽才抛 `NO_SOLUTION_IN_DOMAIN`。

终检 `validate`（`:342-447`）是**独立的一次复核**，有自己的访问预算 `finalValidationVisits = 100 000 000`：检查地块的 4 格对齐、填充群系合法性、面积区间、归属群系与等级，结构的数量区间与两两间距，以及出生点约束。这里有一条重要的软硬之分（`:382-383`）：**配置的最大面积与每个逐格环境/结构约束是硬失败，最小面积在有界多区域恢复之后只是尽力而为**。

群系分配的排序与预算（`BiomeAllocationPlanner.allocate`，`:72-142`）：需求先按“出生地块 → 出生载体 → 地形容量升序 → 目标面积降序 → 等级升序 → patchId”排序，逐个选种、扩张；生长代价是 `0.65 × 有机形状距离 + 128 × 环境代价 + 8 × 噪声 − 3 × 同源支撑数`，温度带距离只作为队列的优先级键。每个“群系/格”的合法性只判定一次并计费，总预算 `BUDGET = 12 000 000`，超限抛 `SEARCH_BUDGET_EXHAUSTED`。

其余类型的分工：

| 类型 | 职责 |
|---|---|
| `PlacementIndex` | 粗候选与精确采样缓存；按等级缓存“允许格”“惩罚”，按步长缓存更细的陆地格 |
| `QuotaAssignment` | **整体二部 b-匹配**：`Demand(id, minimum, candidates[], pinnedCell)`，用交替路径修补贪心抢占而**不丢配额**；失败抛内部类 `CapacityFailure`（含未满足的 demand 列表与访问次数）。**注意：它不在生产路径上**——全仓库调用者只有 `QuotaAssignmentTest` 与 `tools/AllocationReplayAudit.java`（后者不在任何 Gradle source set 里） |
| `BiomeAllocationPlanner` | 竞争生长与多区域恢复；`ConnectedCapacityProbe` 按连通面积探测容量并缓存 |
| `MinimumAreaPolicy` | 两个问题一个地方答：哪些斑块必须免于边界混合（`protectedPatchIds`），以及已达面积是否满足请求（`checkAchievedAreas`，放宽项回调整 sink，违规抛 `NO_SOLUTION_IN_DOMAIN`） |

`FillerLayout` 的构造过程（`planner/FillerLayout.java:43`）值得单独记：先用 16 格网格铺满大陆内干燥陆地，把必需斑块当作**已占障碍**标进网格；把与已有斑块竞争过的前沿继续排入优先队列；然后按“严格最小间距 + 变间距（384–640 格）”撒种子，间距用 `ValueNoise(seed,"filler/frontier",128)` 抽样；`flood()` 做多源生长，优先级是“温度带距离 → 代价 → 种子号 → 格号”；对地形屏障造成的孤立空格再补种；最后 `tidy()`。全部完成后 `snapshot()` 产出 `FillerState`——READY 恢复时直接还原这张网格，不再生长一次（`FillerLayout.java:55`）。

- `ClimateStatistics`　需求统计的接口，声明在 climate 但由 planner 实现（见下）。
- `└─ targetRatios / actualRatios / supply`　三个分开的调用——**刻意不合成一个方法**，因为它们必须在场初始化的不同时刻被调用（见本节"构造顺序本身就是契约"）。
- `ClimatePlan implements ClimateField`　温度场本体；`STEP = 32` 表示它的内部网格是 32 格。
- `├─ OrganicTemperatureField`　"organic-temperature-v7"：世界对齐、与群系需求无关的温度场，也就是新计划的算法。
- `│   applyAsDouble(x,z)`　先把坐标做两层域扭曲，再用两个尺度上的梯度噪声合成场，映射到 `5 + 4.5·tanh(...)`，值域约 (0.5, 9.5)。
- `│   cooling(effectiveHeight)`　高度降温：76 格以上每格降 0.012，110 格以上额外每格降 0.053。
- `│   temperature(x,z,h)`　最终温度：把场值向中心收缩一点、整体加 2.0，再减去高度降温，最后钳到 [0, 10]。
- `├─ FrozenQuartField`　四分格中心值的惰性缓存。只有精确落在格中心的坐标才缓存，其余坐标直接算，以保留精度。
- `├─ snapshot() → ClimateState`　导出可持久化的冻结状态。
- `└─ humidity() → HumidityPlan`　温度场持有湿度场；湿度场在温度场构造的最后一步才被建出来，因为它要用到温度值。
- `HumidityPlan`　湿度场；`STEP = 32` 是它的网格，`REACH = 512` 是距离场的最大有效距离。
- `├─ 以 32 格网格采样地形`　把淡水源（河流、湖泊、湿地）与海水分别记下来，各填一张距离场。
- `├─ 二次扫描八邻域距离变换 spread(...)`　两趟扫描（正向 + 反向）把"水域附近"这个概念传播到整张网格，对角按 √2 计步。
- `├─ weatherOffset`　干燥陆地上天气噪声的均值，用它把天气场中心化。
- `├─ valueAt(x,z,s)`　湿度值 = 天气 + 蒸发（温度越高越干）+ 高程 + 水域邻近加成，结果在 0..1。
- `└─ snapshot() → HumidityState`　导出可持久化的冻结状态。
- `HumiditySupplyCorrection`　**保留的显式策略**：如果填充群系池在某种地形/地貌下根本用不到某个湿度带，就把湿度值吸附到最近的可用带。
- `└─ 按填充群系可用的湿度类型修正湿度值（不是气候推断）`　注意措辞：它改的是湿度值，不改群系的允许湿度集合，也不是"根据温度猜湿度"。

`ClimatePlan` 与 `HumidityPlan` 都接受一个 `frozen` 参数：非空时**只做维度/取值校验后直接采用**，不重算（`HumidityPlan.java:44`）。这是 READY 恢复路径复用冻结环境状态的位置。

`ClimateStatistics` 被注入而不是自己算，理由在接口注释里：需求统计需要作者需求（属于 `planner`）与群系偏好规则（属于 `biome`）。生产实现是 `planner.ClimateDiagnostics`，它在 `JointPlanner`、`BiomeAllocationPlanner` 与 `PlanAssembly` 三处被 new 出来（`JointPlanner.java:76`、`BiomeAllocationPlanner.java:64`、`PlanAssembly.java:45`）。

#### 构造顺序本身就是契约

`ClimatePlan` 的紧凑构造器里，语句顺序不是风格问题，而是**数值正确性**问题（`climate/ClimatePlan.java:118-131`）：

```text
1. angle ← DeterministicRandom.mix(seed) 派生        （只在旧公式里有意义）
2. statisticsSites ← List.copyOf(sites)              ← 先快照站点列表
3. ratios ← statistics.targetRatios(...)             ← 此刻阈值还不存在，用的是未阈值化的 value()
4. snowBoundary ← false
5. angle ← 0；low ← 0；high ← 10；thresholds ← {2.5, 5, 7.5}
6. frozen ← true
7. actual ← statistics.actualRatios(...)             ← 此刻读的是已接受的分带
8. supply ← statistics.supply(...)
9. humidity ← new HumidityPlan(...)
```

**逐句对照**

- `1. angle ← DeterministicRandom.mix(seed) 派生`　先从种子派生一个角度。它只对旧公式有意义（有机场路径会在第 5 步把它覆盖掉）。
- `2. statisticsSites ← List.copyOf(sites)`　把站点列表**快照**下来。后面对场的操作不会影响这次统计。
- `3. ratios ← statistics.targetRatios(...)`　算作者"想要"的温度带比例。**此刻阈值还不存在**，所以它读的是未阈值化的 `value()`——这正是它必须排在第 5 步之前的原因。
- `4. snowBoundary ← false`　雪线标志固定为否：温度是配置出来的，不是降雪测试的结论。
- `5. angle ← 0；low ← 0；high ← 10；thresholds ← {2.5, 5, 7.5}`　确定温度场被接受的形状：不做核心区混合，值域 0–10，四个温度带的分界固定在 2.5 / 5 / 7.5。
- `6. frozen ← true`　标记场已冻结：此后查询走缓存，不再改变。
- `7. actual ← statistics.actualRatios(...)`　算"实际"落在各带的比例。**此刻读的是已接受的分带**，所以它必须排在第 5 步之后。
- `8. supply ← statistics.supply(...)`　算每个需求的合法面积与气候面积，同样是带相关的，排在阈值之后。
- `9. humidity ← new HumidityPlan(...)`　最后建湿度场——它需要温度值参与计算。

接口注释把理由写明了：三部分**刻意分三次调用**，因为场在统计运行时仍在初始化；合成一次调用会把后两项挪到阈值赋值之前，从而悄悄改变发布的统计值（`ClimateStatistics.java:15-19`）。

`snowBoundary` 被固定为 false，注释解释了原因：**温度是配置出来的，不是降雪测试**（`ClimatePlan.java:121`）。有机场路径下 `computeRaw` 直接返回 `organic.temperature(...)`，不做事后修正也不做核心区混合——也就是说“有机温度场”这一代算法完全没有旧的修正项。冻结恢复时对有机态的校验也据此写死：`low==0 && high==10 && thresholds=={2.5,5,7.5}` 且修正列表必须为空（`ClimatePlan.java:86-88`）。

`HumidityPlan` 侧的对应细节：`weatherOffset` 是干燥陆地上天气噪声的均值（`:75`）；湿度值 = 天气 − 蒸发（温度越高越干）− 高程 + 水域邻近加成，再抬一个“距海 96 格内”的下限（`:141-150`）；分带阈值 **0.38 / 0.68**（`:153-156`）；`isShore` 要求距海 ≤ 36 格且地面高出海面 0–7 格，并显式排除 `mountains` 模板（`:173-180`）。湿地列**保留自然湿度**，注释说明理由：填充池不拥有河床与湖床（`:134`）。

### 5.8 `cost`：到达成本与冒险等级

11 个文件，`config`/`Minecraft` 都不引用。

```text
CostPlanner.build(terrain, coastline, spawn, progress)         cost/CostPlanner.java:21
 ├─ spacing = 16（profile.costGridSpacings().getFirst()）
 ├─ 半径取海岸顶点最大模长 + 2 格 → Bounds → 节点数超预算即抛

```

**逐句对照**

- `CostPlanner.build(terrain, coastline, spawn, progress)`　建代价场的入口：参数是地形、海岸线、出生点（源点）与进度回调。
- `├─ spacing = 16`　代价图的网格间距是 16 格，取自 profile。
- `├─ 半径取海岸顶点最大模长 + 2 格 → Bounds`　图的覆盖范围要盖住整块大陆，再留两格余量。
- `├─ 逐节点采样地形，标 allowed[]`　先给每个节点打一个"能不能走"的标记：海、岩浆、危险地形都不能走。
- `├─ BoundaryIntersector：线段与海岸符号距离异号时二分 48 次求交点`　边跨越海岸线时，精确求出交点位置，好让这条边被正确地切成陆段与海段。

- `├─ CostDistanceMap.build(...)`　从出生点做一次完整的单源最短路。
- `└─ AdventureLevels.fromCoast(...)`　用海岸采样点的代价中位数把"成本"折算成 0–10 的冒险等级。
- `　　→ Result(...)`　返回成本场、等级、边的统计、间距、节点数、地形、边界求交器，以及两张惰性细化用的表。

等级的语义：`AdventureLevels.fromCoast` 取**海岸等弧采样点上可达成本的中位数**作为参考值，`level` 的区间是 `coastReference·level/10 ± tolerance·coastReference/10`（tolerance 0.35，即 ±3.5%）；一个采样点不可达就直接不参与中位数，全部不可达才抛 `NO_SOLUTION_IN_DOMAIN`（`cost/AdventureLevels.java:32`）。

`AdventurePreference.penalty(requested, actual)` 是软等级的实现：`0.05·δ² + outside²·(1.6 或 1.0)`，其中 `outside = max(0, |δ| - 0.35)`——**内容出现过早比略晚到更贵**，且没有任何等级被硬禁（`cost/AdventurePreference.java:6`）。这个函数由 `RuntimePlanner` 注入成 `JointPlanner.LevelConstraint.penalty`（`RuntimePlanner.java:110`）。

#### 一条有向边的代价怎么算

`CostDistanceMap` 是**真正的 Dijkstra**（不是 BFS，也不是桶队列）：定容 decrease-key 二进制小顶堆 `PrimitiveMinHeap`，每个节点最多入堆一次，平局按 `(距离, gridX, gridZ)` 确定（`cost/CostDistanceMap.java:168-235`）。源点是出生点，播种时对它所在的 4×4 网格窗口逐个用**真实的有向边代价**连边。松弛用 `Math.addExact`，溢出即抛 `RESOURCE_LIMIT`。

单条有向边的代价（`cost/EdgeCostCalculator.java:25-60`）：

```text
分段：divisions = ceil(length / 8)，参数集合 = 等分点 ∪ 落在 (0,1) 内的海岸交点，排序后 1e-12 去重
阻断：起点/中点/终点只要是危险、海洋或岩浆 → BLOCKED；|坡度| > 2 → BLOCKED
水乘子：dry → 1.0；wet 且水深 ≤ 1.5 → 2.0；否则 → 5.0（取 prev/mid/next 的最大值）
slopeFactor(s) = 1 + 4·max(s,0) + 2·max(-s,0) + 6s²
forward += 段长 × slopeFactor(+坡度) × 水乘子
reverse += 段长 × slopeFactor(-坡度) × 水乘子
量化：max(1, rint(value × 1_000_000))
```

**逐句对照**

- `分段：divisions = ceil(length / 8)`　一条边最多按 8 格切一段，段内坡度才近似恒定。
- `参数集合 = 等分点 ∪ 落在 (0,1) 内的海岸交点`　把等分点和海岸交点合并成一组参数，排序后按 1e-12 去重，避免同一位置算两次。
- `阻断：起点/中点/终点只要是危险、海洋或岩浆 → BLOCKED`　只要端点或中点落在不可通行的地方，整条边双向都不可通行。
- `|坡度| > 2 → BLOCKED`　过陡的段落视为不可通行，而不是给一个很大的代价——这样不会有人"绕上悬崖"。
- `水乘子：dry → 1.0；wet 且水深 ≤ 1.5 → 2.0；否则 → 5.0`　涉水要变贵：浅水两倍、深水五倍。取 prev/mid/next 三个采样中的最大值，避免刚好踩在边界上少算。
- `slopeFactor(s) = 1 + 4·max(s,0) + 2·max(-s,0) + 6s²`　上坡比下坡贵（系数 4 对 2），平方项让陡坡进一步变贵。
- `forward += 段长 × slopeFactor(+坡度) × 水乘子`　正向代价：沿这条边走时把上坡算贵。
- `reverse += 段长 × slopeFactor(-坡度) × 水乘子`　反向代价：坡度取反，所以同一条边两个方向的代价不同——这就是"有向"的含义。
- `量化：max(1, rint(value × 1_000_000))`　统一乘一百万取整成整数，下限为 1；用整数比较保证可复现，也避免浮点误差在松弛过程中累积。

`AdjacentEdgeCache` 用规范化的无向节点对做键，**一次计算同时得出正反两个方向的代价**（`AdjacentEdgeCache.java:32-35`）；对角边额外要求两条正交角路都通（`GridCostGraph.java:15-29`）。粗网格那一遍用定长数组的 `CompactGridCostGraph`（每个规范对正好一个槽位），正是为了避开“数百万个哈希键 + 装箱值 + 对角缓存项”。

细化路径 `refinedCostAt`（`CostPlanner.java:90-93`）按坐标记忆化，每个 256 方块瓦片建一张 33×33 的 8 格网格：粗节点用粗代价播种，**只把周界**用完整 16 格网格的代价播种，内部（尤其是源点本身）保留粗代价作为合法上界——注释解释了为什么（`:129-130`）：只播周界会“发明”一条绕出瓦片再绕回源点的路。

`TerrainTemplate` 的 12 个配方（`terrain/TerrainTemplate.java:30`）是作者可见的词汇：`steppe/plains/dales/hills_1/hills_2/torridonian/plateau/badlands/mountains_1/mountains_2/mountains_3/volcano`，每个带类别、默认权重与垂直振幅，全部归入 `plains/hills/plateau/mountains` 四个规划类别。`TerrainTemplate.Settings` 的紧凑构造器把 `weight ∈ [0,10000]`、`horizontal_scale ∈ [0.25,8]`、`vertical_amplitude ∈ (0,220]`、`detail_strength ∈ [0,2]` 钉死。

`TerrainCapacityPlan` 是“预留 → 消费”的接口面：`Reservation` 记录区域格、模板、最小/最大高度、预留面积、主副配方、允许模板集合、基高、振幅与策略名；`fit(...)`/`acceptsEnvelope(...)` 在高度区间内挑**最大可用包络**，并给出注释说明为什么允许向下搜索盆地（海岸侵蚀淡化出更小的可证界）。`acceptsEnvelope` 把世界边界写死在这里：`low = 64 + base − 0.05·amp ≥ 64`、`high + 8·factor ≤ 318`。

`ExactGridTerrain` 是纯缓存包装（`terrain/ExactGridTerrain.java`），只在精确格点（`x*2` 与 `z*2` 都是精确整数）命中，其余坐标**不量化、直接透传**；`PlanTerrain.withMemoizedQueries()` 用它包住形态层，见 3.4 第 ⑧ 步。

**逐句对照**（调用栈自上而下：上面的一层调用下面的一层）

- `TerrainMorphology.sample(x,z)`　最外层：形态测量。
- `├─ wet() 或 mountainInfluence < 0.15 → 原样返回`　水域与低地不做形态测量，直接把下层的结果原样返回。
- `└─ 否则取 32 格拐点网格的 4 个 Metrics，双线性插值`　在 32 格网格上取四个角点的测量值插值到当前坐标，得到坡度、当地起伏、相对高度。
- `　　└─ measure(): 中心差分坡度 + ±64 八邻域高差与偏差`　每个网格点的测量本身要采样 14 次下层地形。
- `HydrologyTerrain.sample(x,z)`　下一层：水系雕刻。
- `└─ 按 RiverNetwork 重塑水面与河床，产出 RIVER / LAKE / WETLAND`　把冻结的河网作用到地形上，确定这一列是河、湖还是湿地，以及水面在哪。
- `ErodedTerrain.sample(x,z)`　再下一层：侵蚀。
- `└─ ground = base.ground + delta(x,z) × 海岸淡化；湿润样本不叠加`　叠加冻结的侵蚀增量，靠海一侧减弱；已经是水的地方不再叠加。
- `IslandMacroTerrain.sample(x,z)`　再下一层：海岸 + 区域合成。
- `├─ coastDistance(x,z)`　算带符号的海岸距离。
- `│   ← 64×64 瓦片三级饱和，ThreadLocal 记住上一瓦片`　用瓦片缓存把"离海很远"的地方直接判定为饱和值，省掉精确折线距离。
- `├─ regions.sample(x,z) ← 区域配方高度`　问区域采样器要这一点的相对高度与配方信息。
- `└─ sd ≥ 0：ground = seaSurface + smoothstep(sd/landBand) × max(0, relativeHeight)`　陆地：从海平面平滑升到区域高度。
- `　　sd < 0：ground = seaSurface − OceanBathymetry.depth(...)`　海洋：从海平面往下按水深下沉。
- `RegionTerrain.sample(x,z)`　最内层：区域与配方。
- `├─ 域扭曲 warped(x,z)`　先把查询坐标弯曲，让区域边界不是直线网格。
- `├─ 5×5 邻域（ThreadLocal 缓存一整个窗口）`　一次取周围 25 个区域的信息，整个窗口缓存在线程本地。
- `├─ 两趟最近站点选择`　先只搜中央 3×3 建立"最近与次近"的紧界，再用矩形剔除跳过不可能赢的站点。
- `├─ 最近对证明失败则回落 nearestPair(query) 的逐环扩张搜索`　如果剔除的依据不成立，就退回逐环扩张的精确搜索（半径超过 16 就报错，说明证明逻辑出了问题）。
- `├─ 成对权重混合各贡献者高度；细节用独立的 32 格宽度混合`　多个区域交界处按距离权重混合高度；细节分量单独用更窄的宽度混合，避免细节被抹平。
- `├─ transitionWidth(recipe, other)`　两种配方之间的过渡宽度：同配方 96 格，含山地 200 格，含台地或恶地 88 格，其余 144 格。
- `├─ primary/secondary 距离差 < 48 时由 EcotoneSelector 在两者间二选一`　只有在这个窄带里才做"二选一"的生态过渡，第三名及以后永远没有权重。
- `└─ 高度公式：baseElevation + amplitude × (mountain ? (0.15 + 0.85·envelope)·shape : shape)`　山地区域的高度还要乘以山脊走廊包络，非山地直接用配方形状。
- `TerrainRecipes.shape(recipe, x, z, horizontalScale)`　最底层：配方的形状函数。
- `└─ 12 个配方各是一张噪声 DAG；只有 plateau 额外有阶地表面层`　每个配方是一张噪声运算图；只有高原配方会额外叠一层后成阶地表面。

区域本身在首次触达时由 `createRegion` 建立（`RegionTerrain.java:230`），顺序是：中心抖动（`DeterministicRandom("region-center")`）→ 应用容量预留允许的配方集合 → 判定山脊走廊归属（`ranges.influence > .12`，并检查 8 个偏移点，注释说明“由连续包络而非中心点抛硬币决定隆升”）→ 抽取主配方（有预留则直接用预留配方）→ 抽取副配方（受 `FillerTerrainPolicy.sharesFiller` 与 0.6 概率约束）→ 定基高与振幅（有预留则整体被预留值覆盖）。

### 5.10 `hydrology`：河网是怎么长出来的

6 个文件。入口签名：

```java
HydrologyGenerator(PlannerProfile, HydrologyProfile).generate(
    long seed, double radius, double seaSurface, Coastline coast, MacroTerrain baseTerrain)
    → RiverNetwork(channels, wetlands, planner.hydrologyVersion())     hydrology/HydrologyGenerator.java:23
```

主干循环（`hydrology/HydrologyGenerator.java:24`）：

1. **撒河源候选**，最多 2048 次尝试，直到凑够 `profile.mainRiverCount(radius)` 条。每个候选抽 4 个随机量：锚点角、偏转角、锚点半径（`0.24 ~ 0.77 × radius` 的平方根分布）、转向符号；偏转角故意偏离锚点角 0.55–1.40 弧度，“避免所有河流汇入同一个中心”。
2. **二分求出口**：从锚点沿方向以 16 格步长前进，找出仍在海岸内/外的分界，再二分 40 次精化 → `outlet`。
3. **过滤**：长度不足（前 1024 次尝试要求 ≥ 0.48×radius，之后放宽到 0.24）、离世界中心太近（< min(320, 0.18×radius)）、与已有河口距离小于 `mouthSpacing`（前 512 次 0.18×radius，之后 0.10）的候选全部丢弃。
4. **河道生长**：`RiverPath.grow(seed, candidateId, source, outlet, coast, terrain, shape, seaSurface)`，丢弃空路径、与已有几何相交的路径。
5. **水位**：源端水位 = `max(seaSurface + 2, 地面 - minimumBankHeight)`，并沿程施加单调、限坡的水位剖面（`channel(...)` 内的注释说明“先跟随最低周边地形，再施加单调限坡剖面”）。
6. **分叉**：`generateForks(...)` 递归，最多 `maximumForkDepth` 层；父河长度 < 480 或河道总数 ≥ 96 就停；沿程按 0.26 起的变间距布分叉点，每个分叉点最多试 16 个方向候选（方向按 `forkIndex + depth + attempt` 交替取号），分叉长度取父河的 0.25–0.55。
7. **湿地**：每条成功河道都可挂 `maybeWetland(...)`。
8. **河口校验**：`validateMouths(channels, coast, seaSurface)`。
9. 主干不够就抛 `rejected("roots", "bounded irregular river candidates exhausted")`——**宁可失败也不生成半个河网**。

其余类型：`HydrologyProfile` 提供 `main/branch/erosion` 三组形态参数与两个预设实例——`FTF_ADAPTED_V1`（来源校验用固定上游参数）与 `FINITE_CONTINENT`（生产参数，主河数按 `max(2, round(6·min(1, √(radius/3000))))` 随半径缩放，分叉深度 1，湖泊概率 0.18、尺寸 4–30，湿地概率 0.12、尺寸 24–44）；`RiverNetwork` 是 `channels + wetlands + version` 的只读记录；`RiverPath` 负责路径生长；`RiverMorphology` 计算汇流与形态；`HydrologyTerrain` 把 `RiverNetwork` 作用到地形上，产出水位、湿地与列查询。

`RiverNetwork` 把三条几何契约变成了构造期异常（`RiverNetwork.java:14-25`）：三个数组必须等长（`"unaligned river channel arrays"`）、弧长必须严格递增（`"river points must advance downstream"`）、**水位不得在下游上升**（`"river water cannot rise downstream"`）。`HydrologyGenerator` 在返回前还会独立复核后两条，并校验每个主河河口确实落在海岸线上且水位等于海平面（`HydrologyGenerator.java:354-367`）——**宁可失败也不产出半条河网**。

#### 河网到底怎么来的（这一点容易误解）

它不是 flow-accumulation，也不是自河源的 downhill walk 或 priority flood。实际算法是「**拒绝采样 + 地形代价引导的上游生长**」：

1. 撒河源候选（最多 2048 次），几何二分定出河口；
2. 从**河口向河源**生长：每步在 13 个候选方向（±25.8°）里取最优，评分 = 方向偏差 + 目标方向拉力 + 地面起伏代价 + **漫水代价**（`2 × max(0, 水位+最小岸高 − 最低岸高)`，用垂直法向采样取最低岸）；
3. 用折线两两相交检查（含水位差容差）否决候选，最后施加单调、限坡的水位剖面并对主河判定湖泊。

因此“排水量”只以河道长度的形式出现在 `RiverMorphology`（下游剖面由支流树累积得到），并不参与路径选择。`docs/生成流程候选.md:80` 那句“没有移植完整上游水文系统或通用洼地求解”与代码一致：确实没有填洼/全局水位求解。

#### 两条会整体改变下游形态的隐式契约

1. **`HydrologyTerrain` 与 `RiverMorphology` 的噪声种子是 `network.hashCode()`**（`HydrologyTerrain.java:26`、`RiverMorphology.java:17`）。岸线扭曲、沙洲、湖岸与湿地起伏全部是整个 `RiverNetwork` 记录哈希的函数——任何一条河道坐标、甚至 `version` 字符串变化，都会重排所有水体的局部形态。同输入完全可复现，但“改一条小河不影响别处”这个假设不成立。
2. **`ErodedTerrain` 的平滑半径硬编码为 1.8 方块、速率 0.9**（`ErodedTerrain.java:71-79`），而 `HydrologyProfile.Smoothing` 里的 `iterations/radius/rate` 在生产代码里**零读取**（只在该 record 的预设构造与测试 golden 断言里出现）。也就是说改 `Smoothing` 不会改变输出。`ErosionGenerator` 的注释解释了为什么平滑被放在这里而不是增量场里：在持久化 spacing=8 的网格上用 1.8 格核会变成 14.4 方块宽，把丘陵与台地边缘抹掉。

`HydrologyTerrain` 参与 `PlanTerrain.compose`，也是 `GeneratedAdventurePlan.solidSurfaceAt` 的实现来源（`GeneratedAdventurePlan.java:281`）。

### 5.11 `erosion`：冻结的侵蚀增量场

三个文件。核心是“**规划期算好、执行期只查表**”。

```java
ErosionGenerator(PlannerProfile, HydrologyProfile).generate(
    long seed, MacroTerrain terrain, int originX, int originZ,
    int spacing, int width, int height, DoubleConsumer progress) → ErosionDeltaField   erosion/ErosionGenerator.java:29
```

执行顺序：

1. 按 `spacing`（生产用 8，见 `RuntimePlanner.java:81`）把地形采样成 `double[] heights`。
2. 逐 16×16 区块判定：**五点全是海洋就跳过**（省掉远海的工作）。
3. 建 4 线程池，按“颜色”调度：`colorX = chunkX mod 16`、`colorZ = chunkZ mod 16`，同色批次内的区块互不影响，因此**并行调度不改变输出**（注释：默认水滴走 12 格，笔画支撑至多 16 格，所以同色区块互不相交）。
4. 每个区块用自己的 `StableSequence(DeterministicRandom.seed(seed, algorithm,"erosion",task.id,0))` 撒 `dropletsPerChunk()` 滴水滴，逐滴 `erodeDroplet(...)` 累积 `float[] delta`。
5. 返回 `ErosionDeltaField(originX, originZ, spacing, width, height, delta, operations)`。

注释里有一条重要的**不做**：上游的整高平滑被刻意留到 `ErodedTerrain` 在方块分辨率上求值，因为若在这里用 1.8 格核，在持久化的 spacing=8 下会变成 14.4 格宽，把丘陵与高原边缘抹平（`erosion/ErosionGenerator.java:92`）。

`ErodedTerrain` 是作用层：`PlanTerrain.Foundation.eroded(erosion)` 返回它，版本串写死为 `"erosion-v2"`（`PlanTerrain.java:385`）。

### 6.6 测试面的已知薄弱处

## 7．确定性、身份与缓存

### 7.1 一条输入的完整身份链

```text
作者 JSON 文本
 └─ AdventureWorldConfigParser.parse → AdventureWorldConfig
     └─ CanonicalConfigJson.write     固定键序、无多余空白、集合排序
         └─ sha256 → LoadedProfile.configHash          （profile 自身身份）
             └─ PlanIdentity.hash(seed, loaded, adapters)
                 = sha256( canonicalJson
                         ‖ seed
                         ‖ algorithm      = planner-v2
                         ‖ implementation = planner-v2-impl-2026-09-09-…-r33
                         ‖ hydrology      = ftf-hydrology-adapted-v2
                         ‖ terrain        = terrain-r22
                         ‖ adapters       = 排序后的 biome/<id>=<ver> 与 structure/<id>=<ver>
                         ‖ cost           = directed-cost-16x8-v1
                         ‖ erosion        = ftf-erosion-block-units-v2 )
                 → input_sha256，写进 manifest 与载荷
```

**逐句对照**

- `作者 JSON 文本`　这份 profile 的原始文本，来自内置资源或被数据包覆盖的那一份。
- `└─ AdventureWorldConfigParser.parse → AdventureWorldConfig`　解析成不可变的配置对象。
- `　　└─ CanonicalConfigJson.write`　再写成规范 JSON：键序固定、无多余空白、集合排序。
- `　　　　└─ sha256 → LoadedProfile.configHash`　对规范 JSON 求 sha256，作为这份配置自身的身份。
- `　　　　　　└─ PlanIdentity.hash(seed, loaded, adapters)`　再把这层身份与其它生成输入拼起来，算计划的总指纹。
- `　　　　　　　　= sha256( canonicalJson ‖ seed ‖ algorithm ‖ implementation ‖ hydrology ‖ terrain ‖ adapters ‖ cost ‖ erosion )`　`‖` 表示按固定顺序拼接；每一项都是一个版本串或值。
- `　　　　　　　　　　→ input_sha256，写进 manifest 与载荷`　产物同时写在清单与载荷里，读取时两边都要对得上。

因此“改什么会让已有 READY 计划作废”是一个可以逐项回答的问题：改作者 JSON、换种子、改上述任一版本串、增删适配器或改 `adapterVersion()`、改实现修订号——**任一改变都会重新规划**。反过来，改墙钟无关的代码（日志、指标、UI）不会。

`CanonicalConfigJson` 必须稳定（键序固定、默认值补齐、集合排序），因为它是身份的第一项；`AdventureWorldConfigParserTest` 用“`write(parse(write(parse(x))))` 幂等”和“以 `{"biomes":` 开头”钉住了这一点。

### 7.2 随机源

全部随机来自 `DeterministicRandom`（SHA-256 分层抽样）与 `ValueNoise`/`GradientNoise`（同构 key 派生）。两者都不使用 `java.util.Random`，也没有全局可变随机状态。调用点清单见 5.3。`ValueNoise` 的 key = `SHA-256(worldSeed ‖ fieldId)[0..7]`，所以**同一 fieldId 在不同世界给出不同场，同一世界不同 fieldId 相互独立**；fieldId 字符串（`ocean/basins`、`humidity/region`、`filler/frontier`、`query-blend/coarse-x`、`temperature-preview/organic/climate` 等）是地理形状的一部分，改名字就是改地图。

### 7.3 缓存清单

| 缓存 | 位置 | 键 / 失效 | 备注 |
|---|---|---|---|
| `ColumnQueryCache` | `spatial` | SplitMix64(x,z) 取槽，槽内比对完整 key | 定长 2 的幂、无锁；冲突只覆盖；并发未命中允许重复计算 |
| 计划列缓存 | `GeneratedAdventurePlan`（16384 ×2） | 生物群系 / 精确块中心地形 | 生物群系缓存在布局定稿后才创建 |
| `ExactGridTerrain` | `terrain`（262144） | 精确格点 | 只给首次规划的查询栈用 |
| 区域缓存 | `RegionTerrain.regions` | `GridKey` → `Region` | `ConcurrentHashMap`，无限增长但区域数由半径决定 |
| 形态测量缓存 | `TerrainMorphology.measurements` | 32 格格点 → `Metrics` | 每次采样最多 4 个格点 |
| 海岸瓦片缓存 | `IslandMacroTerrain.coastTiles`（16384）+ `ThreadLocal lastCoastTile` | 64 格瓦片 → 饱和标志 | 用 1-Lipschitz 性质把远处的精确折线距离换成常数 |

| 代价图与细化 | `CostPlanner` | 整数采样缓存 262144 + `refinements` `ConcurrentHashMap` | 只对整数/中点端点命中，斜向分数保留精度 |

### 7.4 预算与失败

预算是**操作计数**，不是墙钟：`PlannerProfile.Search` 里是最大代价节点数、最大面积单元数、最大工作内存字节数、保留候选数、必需/可选候选准备数、各阶段状态上界、洪水访问数、地形修复版本数。超限抛 `PlanningFailure`：

- `RESOURCE_LIMIT`：填充网格超预算（`FillerLayout.java:54`）、湿度网格超预算（`HumidityPlan.java:42`）、代价图超内存（`CostPlanner.java:62`）。
- `SEARCH_BUDGET_EXHAUSTED` / `PRECISION_INSUFFICIENT`：搜索类回退用尽。
- `NO_SOLUTION_IN_DOMAIN`：结构准备校验失败、有效面积被混合压到下限以下、海岸参考不可达。
- `UNSUPPORTED_CONTENT`：缺适配器、注册表缺内容、冻结部件无注册类型。
- `CONFIG_CONFLICT` / `CONFIG_ERROR`：作者配置。

`RuntimePlanner` 的类注释写明：**墙钟时间只用于日志，从不作为终止输入**。`PlanningMetrics` 与 `planning-metrics.json` 明确排除在计划字节与身份之外。

22. **`ClimateDiagnostics.distribute` 自己硬编码了分带阈值**：`planner/ClimateDiagnostics.java:91` 用 `2.5/5/7.5` 判带，而同一类的 `actualRatios` 与 `supply` 走 `field.band(...)`。有机场下两者一致（因为 `ClimatePlan` 强制这三个阈值），但若将来出现阈值不同的冻结态，`targetRatios` 与 `actualRatios` 会对同一个站点给出不同的分带。
23. **`HumiditySupplyCorrection` 的掩码按“地形／地貌 + 配方”缓存**（`climate/HumiditySupplyCorrection.java:35-44`）。**【原文已更正】** 原文认为 `TerrainRule.accepts(sample)` 含 `minHeight/maxHeight` 对 `groundSurface` 的判定，因此同键跨高程可能复用到另一高程算出的掩码——这一结论不成立：`correct` 在调用 `rule.accepts(s)` 之前就已经排除了 `minHeight`/`maxHeight` 非空的规则，带高度限制的规则和 shore-only 规则都不参与供给修正；其余准入条件（地形类别、主配方、有无有效次配方、地貌）全部被当前键覆盖，所以缓存键与准入范围是一致的。真实契约是“供给只统计无高度限制、非 shore-only 的填充规则”，属于模板/地貌层面的修正，并不保证该位置所有最终准入条件成立。批次 B 补注释与测试。

25. **`planner` 的失败 stage 字符串与 `PlanningStage` 枚举是两个命名空间**：前者是自由文本（`"structure-in-biome"`、`"final-validation"`、`"competitive-growth"` 等），后者只用于进度广播。写诊断或做自动化匹配时不要混用。
